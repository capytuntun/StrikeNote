# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

StrikeNote (folder name `report_system`, UI title 報告筆記系統): a self-hosted, HackMD-style Markdown note app for pentest/exam reporting. It generates OSCP / OSEP / CPENT-LPT / VHL report templates and two structured Taiwanese "資安院" report modes, and exports paginated PDFs. UI strings and most comments are Traditional Chinese.

## Running

There is no build step, no linter, and no unit-test suite. The front-end is plain static files served by the Node server; a front-end change only needs a browser refresh. The server has exactly one npm dependency, `mysql2` (`npm ci`); the database is **MariaDB** (10.11+).

```
npm ci
node server/server.js                                            # npm start; http://localhost:8080
node server/tools/smoke.js                                       # npm run smoke; end-to-end API exercise against a SCRATCH server
node server/tools/migrate-sqlite-to-mariadb.js --sqlite data.db  # npm run migrate; one-shot import of a pre-MariaDB SQLite file (--dry-run first)
node server/tools/import-md.js --dir ./out --url https://…      # npm run import-md; batch-import a folder of Markdown, images and all (--dry-run, --help)
```

Requires Node 22+. Runtime settings are env vars only, read in `server/config.js`: `PORT`, `HOST`, `DB_HOST`/`DB_PORT`/`DB_SOCKET`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` (the server refuses to start without a password unless a socket is given), `REGISTER_MODE` (open|invite|closed, default invite) and `INVITE_CODE` — both only *starting* values: once an admin changes either in 帳號管理 the `settings` table wins (`server/settings.js`), so editing the env afterwards does nothing — `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `TRUST_PROXY`, `REQUIRE_HTTPS`, `SESSION_TTL_DAYS`, `MIN_PASSWORD_LENGTH`, `MAX_LOGIN_ATTEMPTS`/`LOGIN_LOCKOUT_MINUTES`, `MAX_BODY_BYTES`, `UPLOAD_MAX_BYTES` (default 1 GiB; the whole-file cap for chunked uploads, 0 turns them off), `STORAGE_WARN_MB`/`STORAGE_WARN_PCT`, `TRASH_KEEP_DAYS` (default 30), `LINK_PREVIEW` (default 1; 0 stops the server fetching pages for link preview cards). `deploy/env.example` lists them all with production values. Production is a Raspberry Pi / Debian host provisioned by `deploy/install.sh` (idempotent: re-running it is also the update path), with settings in `/etc/strikenote/env` and TLS terminated by cloudflared or a reverse proxy; see `deploy/README.md`. On first start with no admin, a random admin password is printed once to stdout; in invite mode with no code yet, a random invite code is generated, stored in `settings` and printed once — after that it is shown (and can be changed or regenerated) in 帳號管理, which is also where an admin switches between 邀請制 / 開放註冊 / 關閉註冊.

A local MariaDB for development, with the same settings production uses:

```
docker run -d --name strikenote-db -e MARIADB_ROOT_PASSWORD=root -e MARIADB_DATABASE=strikenote \
  -e MARIADB_USER=strikenote -e MARIADB_PASSWORD=dev -p 127.0.0.1:3307:3306 mariadb:10.11 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci --max-allowed-packet=64M
DB_PORT=3307 DB_PASSWORD=dev PORT=8090 REQUIRE_HTTPS=0 REGISTER_MODE=open node server/server.js
```

A scratch instance is a different `DB_NAME` (or a different container), never the production database. The schema is created and additively upgraded by `db.init()` on every start, so an empty database is all a scratch instance needs.

`smoke.js` is the closest thing to a test suite: one script run top to bottom (there is no way to run a single section), printing PASS/FAIL per check and exiting 1 on any failure. It targets `BASE_URL` (default `http://127.0.0.1:8090`), logs in as `ADMIN_USERNAME`/`ADMIN_PASSWORD` (default `admin` / `scratchpass123`) and self-registers a second user `bob` with an empty invite code, so start the scratch server with `ADMIN_PASSWORD=scratchpass123 REGISTER_MODE=open` on an empty database. Its body-limit check reads `MAX_BODY_BYTES`, so give both processes the same value. `--old` skips the MariaDB-only checks.

Cache busting: every `<script src="js/x.js?v=N">` and the `app.css?v=N` link in `index.html` carry a version query. Bump the number when you change that file. The server already sends `no-store` for its own `.html`/`.css`/`.js` (only `vendor/` is cacheable, for a day), so the bump is the second line of defence against a proxy or CDN edge in between that holds an old copy; keep doing it.

## HARD RULE: never touch real note data

The production MariaDB database, and the pre-migration SQLite file `server/data/data.db` (plus the `server/data-recovery*/` snapshots) still on this machine, hold the user's real exam reports, which are confidential graded evidence. Do not open, query, read, or write any of them, and do not drive the user's logged-in browser tab: on reload the app auto-opens the last note and any `input` event on `#editor` autosaves to the server within ~500 ms, which has already destroyed a real note once. To reproduce or verify anything, use synthetic data in a throwaway harness (a scratch `DB_NAME`/container as above, or serve the static files from another port with no backend, or call `MD.render(...)` / `PDF.showPreview(...)` directly). `server/tools/smoke.js` builds such a fixture; it must only ever be pointed at a scratch server. The migration tool is likewise only ever run by the user against the real file.

## Architecture

### Server (`server/`, one dependency: `mysql2`)

- `server.js` is the only HTTP entry: hand-rolled router for `/api/*`, static file serving from the repo root through an **allow-list** (`STATIC_ALLOW`: only `index.html`, `app.css`, `logo.png`, `favicon.*`, `js/*.js`, `vendor/**`; everything else — `.git/`, `docs/`, `*.md`, `server/` — is 404), security headers, HTTPS redirect behind a proxy, `/api/health` (DB ping, answered before the redirect so a local curl works), 413/400 for oversize/malformed bodies, `uncaughtException`/`unhandledRejection` → log and exit so the supervisor restarts it. It speaks plain HTTP only; TLS is the proxy's job. `server.keepAliveTimeout` (95 s) deliberately outlasts cloudflared's 90 s reuse of idle upstream connections: at Node's default 5 s the two crossed, and a POST sent down a socket Node was just closing came back as a 502 (the proxy only retries GETs by itself). With `TRUST_PROXY=1`, "secure" means `X-Forwarded-Proto: https` **or** Cloudflare's `CF-Visitor` says so, the client IP comes from `CF-Connecting-IP` then `X-Forwarded-For`, and HSTS is only sent on responses that were actually secure. Exactly one instance runs: presence/SSE and the login throttle are in-process.
- `db.js` owns the schema (users, sessions, folders, notes, images, shares, note_versions, book_versions, book_links, settings) and every prepared statement in the `q` object, on a `mysql2` pool. `q.<name>.get/all/run` are **async** (`run` resolves to `{insertId, affectedRows}`); `db.init()` creates the tables (`CREATE TABLE IF NOT EXISTS`, one statement per array element) and applies the additive `MIGRATIONS` list via `addColumnIfMissing` (information_schema, not try/catch). `tx(async fn)` checks out a connection, BEGINs, and binds it through `AsyncLocalStorage` so every `q.*` inside the callback runs on it; a nested `tx` joins the outer one. Deadlocks / lock-wait timeouts / a restarting MariaDB are "busy": retried a few times, then surfaced with `err.busy`, which the router maps to HTTP 503 + `Retry-After` and the client store retries. Two rules for `tx` callbacks: nothing that escapes the transaction (hub broadcasts, timers) may run inside — collect and fire after — and the body must be safe to run twice. Text ids/tokens are `utf8mb4_bin`; `username` is case-insensitive (`utf8mb4_unicode_ci`), so `Admin` and `admin` are one account. `LENGTH()` in the storage statements is bytes; the version/link lists use `CHAR_LENGTH()` because the UI shows characters.
- `api.js` holds all business logic. Authorization rule for the whole file: identity comes from the session, never the body. Note permission is `owner` | `edit` | `read` via `permFor()`: an explicit share row wins, otherwise the note's "general access" (`notes.access` = `restricted` | `site`, with `access_perm`) lets any signed-in user in. There is deliberately no anonymous or link-token access. Folders are private and never shared; an image is readable by anyone who can read a note whose content contains `img:<id>` or `pdf:<id>`; admin endpoints (`/api/admin/users`, `/api/admin/storage`) return account metadata, counts and byte sizes only, never note text.
- **Areas (`notes.area` / `folders.area`, `server/api.js` `AREAS`/`normalizeArea`):** a note's or folder's home is `NULL` (一般 — the dashboard/sidebar tree exactly as before this existed) or one of `'course'` (課程筆記) / `'knowledge'` (知識區) / `'quick'` (隨筆) / `'novel'` (小說), set at creation — `updateNote`'s SQL has no `area` column, so a normal save can never change it, and `resolveArea()` refuses to create a note/folder whose `area` doesn't match the folder it's filed into (a folder's own area is likewise fixed, checked the same way on every move). Three of the four areas ride along in the *same* `GET /api/notes`/`GET /api/folders` response as general notes (cheap to expose, filtered client-side by `.area` — see the front-end bullet below); `'novel'` is the one excluded even from its own owner by the SQL itself (`notesOwned`/`foldersOf`: `area IS NULL OR area <> 'novel'`) until unlocked. **Moving a note between 所有筆記／課程筆記／知識區** (`PUT /api/notes/:id/area` → `moveNoteArea`, `MOVABLE_AREAS = [null, 'course', 'knowledge']`) is the one deliberate way area *does* change after creation — owner-only, validated exactly like `resolveArea` (the target folder, if given, must belong to the target area), and pointedly refuses `'novel'`/`'quick'` on either end: novel stays behind its gate with no back door, and quick notes have no folder concept to land in. It resets `position` to `NULL` (a manual-order slot from the old area's level means nothing in the new one). Reachable from three places that all funnel into the same `js/app.js` `moveNoteToArea()`/`doMoveNoteArea()` — the dashboard's "⋯" menu and the sidebar tree's right-click (both only ever show general notes, so the option is always offered there) and `js/areabrowser.js`'s own row action (wired through `areaOpts().onMoveArea`, offered only when `MOVABLE_AREAS` includes the note's current area) — picking a target area opens `showFolderPicker` scoped to that area's own folders (`o.folders` override), then `refreshViews()` picks the change up everywhere at once since every area's notes/folders are always freshly filtered from `state.notes`/`state.folders`, never cached per-view. **`permFor()` is the single choke point that makes 小說 real protection, not a client-side skin**: `if (note.area === 'novel' && !(owner && novelUnlocked(user))) return null` — the same pattern that already makes a trashed note invisible to every route (versions, images, PDF-via-read, sharing) without each of them special-casing it. `novelUnlocked(user)` checks `user.novelUnlockedAt` (attached onto the user object by `auth.userFromToken` from `sessions.novel_unlocked_at`) is set and fresher than `NOVEL_UNLOCK_TTL_MS` (1 hour). `POST /api/novel/unlock` (`server/auth.js` `unlockNovel`, called from `js/app.js` `promptNovelPassword()`) re-verifies the caller's *own current* password (`auth.verifyPassword`, sharing the login throttle keyed with a `'novel:'` prefix so a wrong novel-password attempt can't lock out real login) and stamps that session's row — **a wrong attempt must answer 403, never 401**: `js/store.js`'s `req()` treats any 401 as "session expired" and force-logs-out via `alert()`, which is the wrong response to a second-factor typo and was live in this codebase once before the fix. A novel note can never be shared or opened site-wide (`setAccess` refuses `area === 'novel'` outright); `js/app.js`'s own `novelIsUnlocked` flag is deliberately never persisted (in-memory only, so every fresh page load re-prompts even if the server-side unlock is still within its hour) — the UX is a per-visit gate, not a per-login-session one. `server/backup.js` round-trips `area` through export/import (`normalizeArea`, re-exported from `api.js`) and refuses to restore a novel note with `access: 'site'` even if the archive claims one.
- `updateNote` distinguishes text changes (bump `rev`, broadcast, touch `updated_at`) from bookkeeping changes (folder move, `meta` such as `pinned`), which are written without any of that. Do not reintroduce the old early return that compared only content and title: it silently dropped folder moves. Because the DB is async, two saves for one note can interleave, so every read-merge-write on a note (`updateNote`, `restoreVersion`, `restoreBookVersion`, `createVersion`) re-reads the row with `q.noteByIdForUpdate` **inside** its transaction and computes from that locked copy; the permission check on the plain read before it is only a pre-check. `restoreBookVersion` is one transaction for the whole book, locking chapters in manifest order. The admin "last admin" guards use `countAdminsLocked` inside the transaction for the same reason.
- Low-disk warning: `storageSummary()` uses `fs.statfs` on MariaDB's data directory (`SELECT @@datadir`, cached by `db.init()`, falling back up the path); thresholds are `STORAGE_WARN_MB` / `STORAGE_WARN_PCT`. The server logs it at start and hourly; admins get a banner from `Admin.checkStorage()` on login. `adminStorage()`'s `dbBytes` is InnoDB data+index size from `information_schema.TABLES`. Backups are `deploy/backup.sh` (`mariadb-dump --single-transaction`), not anything in the app.
- **Backup and restore (`server/backup.js`, `server/zip.js`, `js/backup.js`; 帳號選單 → 備份與還原):** `GET /api/backup?scope=mine|site` streams a zip built by the dependency-free `ZipWriter` (whole entries, real sizes in every local header, UTF-8 names, zip64 only when needed) straight into the response with back-pressure, fetching one note / one image at a time so a big site is never in memory at once. The layout is readable without the app — `notes/<資料夾>/<標題>.md` (trashed under `_垃圾桶/`, site scope under `<username>/`), `files/<id>.<ext>`, `versions/<noteId>/<versionId>.md`, `books/<token>.html` — and the JSON indexes (`folders.json`, `notes.json`, `files.json`, `books.json`, plus `users.json` with scrypt hashes and `settings.json` for `site`) carry ids, timestamps, meta, access, shares and positions. Restore reads only the indexes and the paths they name (`findManifest` tolerates a re-zipped parent directory), so stray entries are ignored. **Restore keeps ids and is idempotent**: missing rows are recreated with their ids and timestamps (`insertNoteFull` etc.), existing rows owned by the caller are skipped unless `overwrite`, which snapshots the current text as a version labelled 還原備份前 first and broadcasts through the hub; an id owned by someone else is a conflict, skipped and reported, never taken over. A `mine` backup always restores into the caller's account; a `site` backup (admin only) maps owners by username, creates missing accounts with their old hashes and keeps existing ones — so the restoring admin's password never changes. Version ids are AUTO_INCREMENT and are remapped into book-version manifests; a book version whose chapters cannot all be resolved is skipped. Uploads come in chunks (`PUT /api/backup/upload/:id?offset=N`, each under `MAX_BODY_BYTES`, refused on an offset mismatch so a retried chunk cannot double-append) into `os.tmpdir()` up to `BACKUP_MAX_BYTES`, then `inspect` returns the manifest for the confirm step and `restore` runs as a background job the client polls — behind a tunnel one request can neither carry 100 MB nor stay open for minutes. One restore runs at a time; temp files and finished jobs are swept after an hour, and leftovers from a crashed process at start.
- **Trash (soft delete):** `DELETE /api/notes/:id` does not delete — it sets `notes.deleted_at` (ms epoch). `permFor()` treats a row with `deleted_at` as non-existent, so every normal route (read, save, versions, shares, image visibility, listings) 404s on a trashed note without each of them having to know; only `GET/DELETE /api/trash`, `DELETE /api/trash/:id` and `POST /api/notes/:id/restore` look at those rows, owner-only. Shares, versions and images stay attached, so restore is a one-column update; `q.restoreNote` also nulls a `folder_id` whose folder was deleted meanwhile, otherwise the note would come back invisible. Hard deletes (`q.deleteNote`, FK cascades) happen only on purge, empty-trash, or the hourly `purgeTrash` sweep in `server.js` after `TRASH_KEEP_DAYS`. The client side is a full page, not a dialog: `openTrash()` in `app.js` (the sidebar's 垃圾桶 row, or `#trash`) hides the other views and shows `#trash-wrap`, and `Trash.render(container, opts)` in `js/trash.js` draws a dashboard-style page into it (breadcrumb head, a separate section for notes within 3 days of purge, per-row and checkbox-batch restore/purge, search, 清空垃圾桶). `showEmpty`/`openNote`/`openBook` hide it again. Like the dashboard it keeps the sidebar drawer open (`openTrash` opens it, and the click-outside rule in `initSidebarDrawer` skips both views), and `refreshViews()` re-renders it while it is visible so a note deleted from the sidebar appears without a reload. `app.js`'s "delete" paths just call `Store.deleteNote` and re-word the confirm. Deleting a folder still deletes the folder row outright — only its notes go to the trash.
- `auth.js`: scrypt passwords, sessions stored as SHA-256 of a random token in an HttpOnly SameSite=Strict cookie `rn_session`, per-username+IP login throttling. CSRF is a custom `X-Requested-With` header check on non-GET requests.
- `hub.js`: in-memory Server-Sent Events fan-out per note id (`/api/notes/:id/events`) carrying `update`, `presence`, and `cursor` events. Nothing is persisted.
- **`js/merge.js` is the one merge, for both sides** (`server/merge.js` is a one-line `require('../js/merge.js')`; the file is a UMD wrapper — `module.exports` under Node, `window.Merge` in the browser). Client and server must resolve every conflict identically or two editors never converge; there used to be two hand-synced copies. `merge3(base, mine, theirs)` works in three levels, each only where the level above found both sides touching the same region: **lines** (`lineHunks`: LCS on the middle after trimming the common start/end — typing touches a few lines, so a 5000-line note merges in ~1.5 ms instead of an O(lines²) table under the row lock — then `slideHunks`, then `coarsenLines`, which joins line hunks separated only by one line or up to three blank/near-blank lines, because the LCS likes to pair some blank line with another and describe "edited these lines" as "deleted them, re-inserted edited copies further down", which duplicated or dropped the other person's edit of the same lines), then **tokens** (`tokenize`: ASCII words, runs of spaces, `\n`, and every other code point — CJK, punctuation, emoji — on its own; char-level LCS paired the letters of a new word with an old one next to it and cut both apart, which in a three-way merge interleaved two people's text), then **characters** inside the few words both sides changed (`mergeLetters`: "b"→"Xb" and "b"→"bY" is "XbY"). `slideHunks` moves every pure insertion/deletion to the position with the most natural boundaries on both sides (line break > space > punctuation, diff-match-patch style) so two people inserting at "the same place" really land on one spot, and joins same-side hunks it brings together. Conflicts: hunks that `overlaps()` (overlapping ranges, an insertion strictly inside the other's range, or two insertions at the same point — that last case must stay a conflict, see below) are grouped transitively by `combine`, whose output is checked for overlap and falls back to the old drop-theirs rule if it ever broke. At the character level an edit of the very same characters goes to mine — **unless one side only deleted there**, then both deletions stand and the other side's new text goes in (operation-based editors do the same with delete vs. retype: two people removing the same lines while one typed at their edge keep what was typed). **Same-spot insertions (`sameSpot`) keep both, mine first**, except: one side already contains the other's text → that side; a shared start/end with at least `SHARED` (20) non-space characters → the shared part once plus both differing middles (a short shared run like a space or "- " is not factored, or "the cat"/"the dog" would splice into "the catdog"); bigger than `BOTH_CHARS`/`BOTH_LINES` → mine wins; for characters, a part ending in `\n` goes first. Those containment and size rules are what keep the old failure from coming back: a save measured against a stale or empty `baseContent` "inserts" text the server already has at the same point, and blindly keeping both once took a note from ~15 KB to 1.5 MB under 50 concurrent saves (with `overlaps()` treating same-point insertions as conflicts at all, which must stay). `toText`/`fromText` hand a line region to the token merge with **every line carrying its own newline**, so "no lines" and "one empty line" stay different (joined plainly, two people deleting the same line left an empty line). `mapOffset(oldText, newText, offset)` maps a caret through a change the same way (by line; inside a changed line token by token, and letter by letter inside a changed word; text inserted exactly at the caret stays after it) — see the collaboration bullet. The scratchpad suite that covers all of this (fixed cases, random property checks, a full protocol simulation of 2–4 clients with out-of-order replies and SSE, an insert-only run where every typed token must survive exactly once, the stale-base snowball, and timing) is `merge-test.js`/`merge-debug.js`; `smoke.js` has API-level checks (same line → both kept, same spot → both kept, stale-base save → no duplication).

### Front-end (`index.html` + `js/` + `app.css`, vanilla JS)

Every module is an IIFE that publishes one global (`Icons`, `Store`, `Auth`, `MD`, `Editor`, `Templates`, `EditorHL`, `TableTool`, `OSCP`, `SecReport`, `SecEditor`, `PerfReport`, `Dashboard`, `Annotate`, `PDF`, `Search`, `Admin`, `Migrate`, `Merge`, `Book`, `MindMap`, `Versions`, `Trash`, `ImageLib`, `Graph`, `LineSync`, `App`). Load order in `index.html` matters because later scripts call earlier globals; `app.js` is last and orchestrates everything (tree, view modes, autosave, sharing UI, PDF button, paste/drop upload, book mode entry).

- **The markdown editor is always dark**, in both themes — it is a code surface, and only the preview follows the light/dark toggle. Its colours live in the `--ed-*` tokens defined once on `:root` with no `[data-theme="dark"]` overrides; every rule under `.edit-toolbar` / `.editor-area` / `.cm-*` / `#editor` must use those tokens, never `--bg` / `--text` / `--border`, or the editor will go light-on-dark.
- **The editor's syntax highlighting is a separate overlay (`edithl.js`) laid out independently of the textarea.** `#editor` is `color: transparent`; what you see is `.cm-lines` (one `.cm-row` per source line) drawn behind it, kept in step only by `translateY(-scrollTop)` and by both boxes having identical wrap width and identical row heights. Anything that makes a single `.cm-row` differ from the textarea's 31.5px line (e.g. a row with no line box — an empty `<span>` collapses to the 28px gutter — or a line that wraps at a different width) shifts every row below it, and the caret/selection visibly lands on the "wrong" line a few hundred lines down. Hence: blank lines always get a U+200B so they keep a line box, and `--sbw` is measured live from `ta.offsetWidth - ta.clientWidth` on every render (same trick as `syncMirrorStyle` in `app.js`). To check a note, compare `#editor.scrollHeight` with `.cm-lines`' height — they must agree to within 1px.
- **The app shell must never scroll; only the inner panes do.** `#app` is a fixed-height (`100vh`) flex column — `#topbar` (fixed 52px) then `#app-body` — and `html`, `body`, `#app` and `#app-body` are all `overflow: clip`, **and `body` is `position: relative`**. Both halves are load-bearing. On an element, `clip` (not `hidden`) means "not a scroll container", so a `scrollIntoView`/`focus()` skips `#app`/`#app-body` and walks up to the viewport — but `overflow: clip` on `html` is applied to the *viewport* as `hidden` (css-overflow-3), and `hidden` still allows programmatic scrolling. Measured in Chrome 152: with anything sticking out below the fold, `window.scrollTo` and a preview heading's `scrollIntoView({block:'start'})` (the TOC click in `app.js`) both moved `document.scrollingElement`, the latter by exactly the topbar height. So the real guarantee is that *nothing can ever extend past the viewport*: `body` is positioned so an absolutely-positioned body child is contained by `body`'s clip instead of escaping to the initial containing block and growing the viewport's scrollable overflow. That escape was the actual bug behind three fixes (`0bf3904`, `8a206d3`, this one): the caret-measuring mirror `<div>`s in `js/editor.js` (slash popup) and `js/table.js` (table toolbar) are appended to `body` once and cached, copy the textarea's `height`, and were `position: absolute` with no offsets — from the first `/` onward they sat just below `#app`, ~editor height tall, and the next TOC click scrolled the whole shell up 52px: topbar gone, `body`'s background as a strip under the statusbar (reads as "the footer got bigger"). They are `position: fixed; top:0; left:0` now. Rules: anything appended to `body` must be `position: fixed` (every overlay, popup and toast already is); to check a live page, `document.scrollingElement.scrollHeight` must equal `clientHeight`, and if it doesn't, list `document.body.children` for the one with a height below the fold. Chrome clamps `scrollTop` back to 0 the moment the overflow disappears, so the symptom sticks only while the stray element persists. `#app` is `position: relative` for the same containment reason. Scrolling lives entirely in the inner panes (`#editor`, `.preview-scroll`, `.empty-state`, `.trash-wrap`, `.sec-editor-scroll`, `.book-*`).
- **The topbar collapses progressively as it runs out of room (`fitTopbar()` in `app.js`),** not at viewport breakpoints: it measures whether the absolutely-positioned title actually collides with the mode-switch or the right-hand buttons — and, once the title is hidden, whether `#topbar` itself still overflows — and escalates through `topbar-lvl1`…`topbar-lvl5` on `#topbar` until it fits, re-checking after each step so it also relaxes back down when there's room again. Measuring beats a fixed `@media` width because what actually matters is the topbar's own content width, which changes with the note title's length and with how many mode buttons exist — a title-width-only check doesn't see a mode-switch that's grown wider. Called from `fitNoteTitle()`, on window resize, and from a `ResizeObserver` on `#topbar`. Each level hides one more thing, least-costly first: lvl1 the capybara/presence (pure decoration); then, before any label goes, `capTitle()` narrows `.note-title-wrap` (inline `max-width`, down to `TITLE_MIN` 240px) to the room between the mid-line and the nearer button cluster, so a long folder path is cut to `…/` instead — without that step a note in a deeply named folder lost every button label at an ordinary 1500px laptop width; lvl2 the mode-switch and 版本/分享/PDF button labels (icons only), after which `capTitle()` runs again with the room that freed; lvl3 the title itself (and the now-pointless 80px title spacer, which is `min-width` load-bearing only while the title needs balancing) — checking `visibility:hidden` here matters, else the hidden title's stale position keeps failing the fit check forever; lvl4 collapses 版本/分享/PDF into one `#topbar-more-btn` (its handler must `stopPropagation()`, same as every other `openMenuAt` trigger, or the same click's bubble to `document`'s `hideCtx` closes the menu it just opened) and drops the username text; lvl5 drops the `StrikeNote` wordmark, keeping the mark. Split view itself stays a flat 50/50 below that — an editor and preview pane both need real width, and 編輯/預覽-only remain the user's own way out at that point.

Changing that size means changing `.note-title-measure` in the same commit — `fitNoteTitle()` sizes the input from that hidden span, so a mismatch measures the wrong width. **The shrink order is the part that actually matters**: when the group runs out of room the *title* is what truncates, never the folder. Flex has no "shrink A first, then B", since shrinkage is shared in proportion to `flex-shrink × basis` — so the priority is expressed as a weight, `flex: 0 1000 auto` on `#topbar .note-title` against `flex: 0 1 auto` on `#note-path`: essentially all the overflow lands on the title (which ellipsises), and the path only starts giving way once the title has hit its 40px `min-width`. It was the other way round once (`flex-shrink: 0` on the title), and flex then crushed the whole folder prefix to zero width to fit a title that refused to shrink — on screen that left just a sliver of an artefact before the title and no folder name at all, which is exactly what a user reported from a real report. Plain `flex: 0 0 auto` on the path is *not* the fix either: a long folder name (its own `.note-path-text` cap is 30vw) plus the title's 40px minimum then overruns `.note-title-wrap`, and the wrap's `overflow: hidden` slices the title off with no `…` at all. The title input has no fixed width of its own: `fitNoteTitle()` in `app.js` measures the current value (or placeholder) in a hidden `.note-title-measure` span with the same font and sets `style.width` — it runs on open, on every `input`, on remote/rename title changes and after `document.fonts.ready`. - **Collaboration flow:** `app.js` tracks `_syncRev`/`_syncContent` for the open note and sends them as `baseRev`/`baseContent` on every autosave. The server merges against the current row, bumps `rev`, and broadcasts; the client merges incoming updates (SSE pushes and save replies alike, through `applyRemoteUpdate`) into the live textarea with the same `merge3`, dropping any whose `rev` it already has. **Only one save per note is ever in flight** (`saveNow` → `sendSave` → `afterSave`: a save that finds `_saving` set is queued in `_saveAgain`, SSE updates arriving meanwhile are held in `_heldRemote`), and the merge base for a save's reply is the text that save *sent*, not the older `_syncContent`. While anyone else has the note open (`collaborators`, from the presence list) the autosave delay drops from `SAVE_DELAY` 500 ms to `SAVE_DELAY_SHARED` 150 ms — that half second was also how late the others saw each word (measured A→B: ~570 ms → ~200 ms on a local server); still one save in flight at a time. **Carets go through `Merge.mapOffset`**, not a common-prefix/suffix guess: with edits both above and below the caret (two other people typing) the old mapping threw it back to the first edit and the next keystrokes landed inside someone else's words — a three-person typing test garbled half its markers until this; `applyMergedToEditor` maps both ends of a selection. Remote carets are offsets into *my* text, so `shiftRemoteCarets` moves them through every change of it (my typing, a merge); before, someone parked at the end of line 5 slid into line 4 as I typed above them. Both halves are load-bearing: with two saves overlapping — routine over a slow Cloudflare Tunnel — the second one's base predated the first, so the server and then the client each merged the first save's own insertion in a second time (click Code, paste before that autosave returns → the closing ```` ``` ```` came out twice).
- **Markdown pipeline (`markdown.js`):** marked (`breaks: true` — HackMD semantics, a source newline is a `<br>`; do not "fix" this back to the CommonMark default, users write one sentence per line and expect the preview to match the editor) + DOMPurify + highlight.js with custom tokenizer extensions for GitHub `> [!NOTE]` callouts, HackMD `:::info` containers (aliased onto the same callout HTML), `RISK:` callouts, `[toc]`, and ` ```lang= ` line-number fences. A fence with **no language** is highlighted through the **bash** grammar (`autoShell`, `ignoreIllegals: true`) with no visible language label — not `highlightAuto`, which was removed because it confidently mislabels pentest content (measured: `whoami` output → SQL with 69 spans, an NTLM hash → Ruby, a Cobalt Strike log → SQL). bash is safe *because* it is conservative: pasted terminal output (nmap/whoami/mimikatz/ls dumps, hashes) comes back with 0–1 spans and stays visually plain, while actual commands get their `#` comments / `"strings"` / `$vars` tinted; the label is left blank so an untagged block never claims to be bash. A setext underline that is a lone `-` does not make a heading (the `lheading` tokenizer override): under a list item that line is someone starting an empty sub-bullet, and CommonMark would turn the parent item's text into an `<h2>`. One indent level in `editor.js` is 4 spaces, and on a list line Tab/Shift+Tab move the whole line a level wherever the caret is. Images are referenced as `![alt](img:<id>)` and embedded PDFs as `![name](pdf:<id>)`; rendering resolves them through `Store.getImageBlob`, a session-lifetime cache of raw image bytes keyed by id that both the preview (`MD.resolveImages`) and PDF export (`MD.inlineImagesAsDataURL`) share, so an image-heavy note is fetched once total instead of once per surface. The cache holds the in-flight *promise*, not just the settled blob: `resolveImages` walks every `<img data-img-id>` synchronously, so a report that reuses one small icon several times issues that many `getImageBlob` calls before the first can possibly have resolved — caching only the settled value (the bug this replaced) let every one of them race past the empty cache and fire its own redundant GET, each competing for the same handful of per-origin connections; over a flaky link that's what turns "open a note with a repeated icon" into everything sitting broken for tens of seconds before popping in together. A rejected fetch deletes itself from the cache (checking the cached entry is still *this* promise before deleting, so a slow failure can't clobber a newer request already in flight) so the next caller gets a fresh attempt instead of a permanently poisoned `null`. `Store.getImage` (blob + `/meta`, for shapes/`canAnnotate`) stays the annotation editor's own call, since it is the only caller that needs metadata; `MD.invalidateImage`/`Store.invalidateImage` drop an id from the cache after annotation rewrites it.
- **Multi-line editing (`js/multicursor.js`), HackMD/Sublime style:** Alt+drag for a column (rectangular) selection, Alt+click to add or remove a cursor, Ctrl+Alt+↑/↓ to add one on the line above/below, Ctrl+D to take the next occurrence of the selection (first press selects the word under the caret), Esc or a plain click to go back to one. A `<textarea>` has exactly one selection, so **the main cursor stays the native one** — it blinks, it scrolls the view, the browser owns it — and the others are drawn on a `.mc-layer` over the editor from `Editor.caretCoords` (minus `scrollTop`); only the extras live in the module, and `all()` merges them with the textarea's own selection on demand. Every edit is applied to each cursor in document order through `document.execCommand('insertText'/'delete')` with a running offset shift, so **native undo still works** and `input` fires per step, which means autosave, preview, the highlight overlay and the collaboration path need no special case. The write path is hooked on **`beforeinput`** (typing, programmatic `insertText`, dropped text all pass through it; keydown alone missed everything that is not a physical key) plus `keydown` for the keys that never reach it (Enter/Tab/Backspace/Delete are also caught there first, with `stopPropagation`, so `editor.js`'s smart-Enter and auto-pairs do not fight the multi-cursor path) — `applying` guards against re-entering on our own `execCommand`. IME: only the main cursor composes; the composed string is replayed at the other cursors on `compositionend`. Paste splits across cursors when the clipboard has exactly one line per cursor, otherwise every cursor gets the whole text; copy/cut join the pieces with newlines. `mouseup` is bound to the **document**, not the textarea: a drag usually ends outside the editor (edge, autoscroll) and binding it to the textarea left the native cross-line selection in place, so the next keystroke replaced everything between the two ends. A remote merge calls `remap(oldText, newText)`, which moves every extra cursor with `Merge.mapOffset`, the same mapping the caret and remote carets use. Attached to `#editor` only; the status bar shows "N 個游標（Esc 取消）".
- **Editor/preview line sync (`linesync.js`):** click a line on either side and that line is underlined on *both* sides — the editor row and the matching preview text, image or code line. Deliberately a companion pass outside `markdown.js` — it never touches `MD.render()`, a renderer, or an extension, so it cannot affect PDF export, the published e-book, or search, none of which call it. It takes the note's top-level blocks from `marked.lexer()` — the same `marked` instance, so the callout/container/RISK/`[toc]` extensions are included and each token is exactly one rendered block — finds each token's `raw` in the source (after the same CRLF and leading-tab normalisation marked applies) for its line range, and pairs tokens with the already-rendered preview DOM by *position* per kind — the Nth heading token with the Nth outermost `<h1..h6>`, and so on — the same idea `app.js`'s own `editorBlocks()`/`previewBlocks()` use for the split-view scroll anchors. Do not go back to a hand-written block scanner: the first version had one, and every construct where it disagreed with marked (a `<br>` or other raw-HTML line, indented code, a setext heading, a lazy continuation line, text right after a table, a pipe-less table, a link definition) added a phantom paragraph, so every later paragraph underlined its neighbour — and a lone `| grep` line looped forever. Elements are matched *outermost*, not as direct children, because a raw-HTML wrapper (`<details>`, `<div align="center">`) can enclose markdown blocks; the blocks a raw `html` token produces itself are counted in a `<template>` and skipped. Paragraphs and list items get split further at each `<br>` (breaks:true's one-newline-one-`<br>` guarantee, plus one more per literal `<br>` typed on a line), and un-numbered code blocks at each newline inside their `<code>` (line-numbered code already has one `<li>` per line), into one `<span class="sync-ln" data-line0 data-line1">` per source line, reusing `markdown.js`'s `splitHighlightedLines` tag-stack trick (generalized from splitting on `\n` to splitting on `<br>`, and from `<span>`-only to any tag, with void elements like `<img>`/`<input>` excluded from the open-tag stack since they have no closing tag to balance). Blockquote/callout/RISK-finding/mindmap blocks — and a code block as a whole, for its fence lines — are tagged as ONE coarse range instead — not addressable line-by-line the way plain text is — and a list item's own text is refined the same way but a *nested* sub-list inside it is left completely untouched, falling back to the outer `<li>`'s own coarse range. Every tagged element carries `data-line0`/`data-line1` directly (coarse containers *and*, where refined, the inner spans within them), so a preview click is just `closest('[data-line0]')` — nearest ancestor naturally wins over the coarser one further out. The editor side has no per-line DOM of its own; it reuses `edithl.js`'s existing one-`.cm-row`-per-source-line overlay purely as a paint target (a `.sync-hit` class), without changing `edithl.js` — and because edithl replaces every row on each input and resize, a `MutationObserver` on `.cm-lines` puts the class back. Both sides go through one `showHit(start, end)`: the editor rows for that range plus every preview element tagged with exactly that range, minus any element containing another hit (a one-line `<p>` and its own span share a range, and only `.sync-ln` is styled). In the preview a text line gets an underline, an image or PDF embed a bar under it (`text-decoration` cannot paint under a replaced element), a coarse block a bottom rule. Rebuilt on every `renderPreviewNow()`; afterwards, while the editor has focus the underline is re-derived from the caret, otherwise it is dropped on both sides, since the same line numbers may no longer hold the same text. In `renderPreviewNow()` it must run *before* `MD.resolveImages()`: splitting a paragraph or list item rewrites its `innerHTML`, which replaces its `<img>` elements, and on a cache miss `resolveImages` sets `src` asynchronously — in the other order the `src` lands on the discarded element, so every image in a paragraph or list item is blank when a note is opened and only appears after the next keystroke re-renders from cache (images in tables and callouts are unaffected, which makes it look intermittent).
- **PDF export (`pdf.js`):** builds a standalone HTML document (cover, TOC with page numbers, themes, watermark) and paginates it with `vendor/paged.polyfill.js` inside a same-origin iframe written via `document.write`, then prints. The in-app preview and the printed output are the same document.
- **Image library (`js/imagelib.js`, `GET /api/images` → `api.js:listImages`):** the 圖片管理 row at the bottom of the sidebar opens a gallery of every upload the caller owns (images and PDFs; metadata only) with the notes each one appears in, filtered as 全部 / 使用中 / 未使用 / 僅在垃圾桶 and, through a note picker (or the funnel on each 使用於 row), by note. The picker's list is the union of `images[].notes`, so it only offers notes the caller can see, and the status counts and footer totals follow the chosen note. "Used" is decided exactly like image visibility — `img:<id>` or `pdf:<id>` anywhere in note content — but over *every* note regardless of owner (`q.notesEmbeddingMedia` is only an `INSTR` prefilter; the exact matching is the `MEDIA_REF` regex), because an upload pasted into someone else's note is still in use and must not be offered as unused. A note the caller cannot read only increments `hiddenNotes`: never named, and its alt text never becomes the image's `name`. The caller's own trashed notes are returned with `trashed: true`, which is what 僅在垃圾桶 means. Note *versions* are not scanned, so an image shown as unused may still be referenced by an old version. Images have no trash; deleting is the existing `DELETE /api/images/:id`, one request per selected file. Thumbnails load straight from `/api/images/<id>` (`loading=lazy`), deliberately not through `Store.getImageBlob`, whose cache lives for the whole session; each card's DOM is built once per id and re-parented on filter/sort changes, so thumbnails never reload. The dialog's keydown listener is on the capture phase because `App.confirm` also listens there and removes itself first — on bubble, the same Esc that closed the confirm would then close the library too.
- **檔案管理 is also a small cloud drive: its own folder tree, independent of notes (`server/db.js` table `file_folders`, `images.folder_id`).** Deliberately a *separate* table from the notes' `folders`, not a fifth `area` — an area's whole reason to exist is note visibility rules (`permFor`, `novelUnlocked`, the `AREAS` union in `resolveArea`), none of which has anything to do with organising uploads, and folding file folders into that system would drag them into all of it for nothing. `file_folders` is the bare minimum: `id`/`owner_id`/`name`/`parent_id`, no `area`, no sharing (檔案管理 was already private-per-caller before this). `GET/POST /api/file-folders`, `PUT/DELETE /api/file-folders/:id` (`server/api.js` `listFileFolders`/`createFileFolder`/`updateFileFolder`/`deleteFileFolder`) mirror the notes-folder endpoints' shape one-for-one. **Uploading into a folder is additive, not a new upload path**: `POST /api/images` gained an optional `X-Folder-Id` header and `POST /api/uploads` (chunked start) an optional `folderId` body field, both resolved through `resolveFileFolder()` (an id that isn't the caller's own, or doesn't exist, quietly resolves to `null` — the drive root — rather than erroring, the same forgiving stance `resolveArea` does not take for notes because here there is no visibility rule being bypassed, just a display location); every *existing* caller (paste, drop, toolbar 檔案, the course-file uploader) omits it and keeps landing at the root exactly as before. Renaming and moving are `PUT /api/images/:id/file` (`server/api.js` `updateFile`, `{name?, folderId?}`) — a deliberately separate path from the existing `PUT /api/images/:id` (`saveImage`, annotation: rewrites `data`/`original`/`shapes`, owner-only, refuses a chunked file) so a chunked (big) upload can still be renamed and moved even though it can never be annotated. **Deleting a folder cannot destroy anything**: images have no trash (`imgLib`'s own delete confirm says so plainly), so `deleteFileFolder` (`tx`-wrapped) moves every direct child folder and every file inside up to the deleted folder's own parent *before* deleting the row — a cascade of empty-folder deletes only ever flattens the tree by one level each time, never drops a file. `js/imagelib.js` reuses the dashboard's own folder-tile and breadcrumb classes (`.dash-folder-tile`, `.dash-crumbs`/`.dash-crumb`) rather than inventing a look, the same reuse `areabrowser.js` already does for 課程筆記 — `.imglib-folder-grid`/`.imglib-crumb` supply only the spacing, all the visual language is free. Browsing is folder-scoped (`matches()`'s `folderScoped()` check: a file only shows if `img.folderId` equals the browsed folder) *unless* a search query or the note-filter is active, in which case scope is dropped entirely — searching or filtering by note means "find it no matter where it is," not "find it in the folder I happen to be looking at." Drag-and-drop speaks two channels at once on the same elements: `DRAG_MIME` (`application/x-strikenote-files`, a JSON array of file ids — the files version of `dashboard.js`'s own private MIME types) for dragging a card onto a folder tile or a breadcrumb crumb to move it, and the browser's native `Files` type for dragging real files in from the OS to upload into whatever tile or breadcrumb crumb they're dropped on (or the open grid background, which uploads into whichever folder is currently browsed) — `hasFiles`/`hasInternalDrag` tell the two apart on `dragover` so a tile's drop handler does the right thing either way. **A real regression this shipped with and smoke.js now guards against**: `images.folder_id` added a trailing bound parameter to `insertImagePending`/`insertImage`'s SQL, and `server/backup.js`'s two restore call sites (recreating a missing file's row) were not updated to pass it — every restore then failed outright with mysql2's "Malformed communication packet" (a bound-parameter-count mismatch), caught by `npm run smoke`'s backup-restore section before anyone else could hit it. Restore now passes `null` (drive root) for the parameter; **backup/restore does not yet carry a file's folder placement** — a restored file always lands at the top level, not wherever it was filed before the backup, which is a known, accepted gap rather than something backup.js silently gets wrong.
- **Uploads are any file, and serving decides what a file may do.** `POST /api/images` takes any `Content-Type` (sanitised by `uploadMime`) plus the original name percent-encoded in `X-File-Name` (`images.name`). `server.js:sendUpload` serves only inert types as themselves — raster images, `application/pdf` (the in-note viewer needs it inline), SVG under a `sandbox` CSP — and everything else as an `application/octet-stream` attachment with `Content-Disposition` and `sandbox`. Keep it that way for every route that returns stored bytes (`/original` too): served under its claimed type, an uploaded `.js` satisfies `script-src 'self'` and an uploaded page runs in the app's origin. In notes: `![alt](img:<id>)` embeds an image, `![名稱](pdf:<id>)` embeds a PDF viewer, `[名稱](pdf:<id>)` shows the same PDF as a file link, `[名稱](file:<id>)` is any other attachment (`fileChipHTML` in `markdown.js`, via marked's `link` renderer, which returns `false` for ordinary links). Visibility and the library's "used" check (`getImage`, `MEDIA_REF`, `notesEmbeddingMedia`) know all three schemes; a new scheme must be added to all of them or its files 404 for share recipients and show as unused. Every upload path — paste, drop, toolbar 檔案, `/file`, and the library's own 上傳檔案 — goes through `uploadFiles` in `app.js`. The sidebar entry and dialog are 檔案管理 (`imagelib.js`, still `ImageLib`, still `/api/images`).
- **Big files are chunked end to end (`image_chunks`, `POST /api/uploads` → `PUT /api/uploads/:id/:seq` → `POST …/finish`).** One request is capped by `MAX_BODY_BYTES`, one MariaDB packet by `max_allowed_packet` (64M) and one request through Cloudflare by 100 MB, so a lecture video cannot go through `POST /api/images`. `Store.uploadFile(file, onProgress, mime)` sends anything over 20 MB (or anything the direct path refuses — the browser sees a status-less "Failed to fetch", not a 413, when the server hangs up mid-body) as `UPLOAD_CHUNK`-sized pieces (8 MiB, never more than `MAX_BODY_BYTES`; the server names the size, the client never assumes it), in order, one at a time. Each piece is its own `image_chunks(image_id, seq, data)` row; the `images` row carries `size`/`chunk_size` with an empty `data`, and stays `pending = 1` — invisible to `getImage`, the library, storage totals and backup — until `finishUpload` has counted every byte. `putChunk` insists on the exact expected length, acknowledges a repeat of a chunk it already holds (`seq < have` → `{next}`) instead of appending twice, and answers a chunk ahead of its turn with 409 + `next`, which is how a client that lost a reply resumes (`send()` in `server.js` passes `next` through on an error body for exactly this). Abandoned pending rows are swept hourly (`sweepPendingUploads`, from `purgeTrash`). **Serving** (`server.js:sendChunked`) streams the rows one at a time with back-pressure and honours a single `Range` (206 / 416, `Accept-Ranges: bytes`) — that is what makes a `<video>` seekable and lets Chrome find an MP4's trailing `moov`; type handling is the same `uploadHeaders()` as small files, so a chunked `.html` is still an `octet-stream` attachment under `sandbox`, and only `video/(mp4|webm|ogg)` and the listed `audio/*` types were added to `INLINE_UPLOAD`. A chunked file cannot be annotated (`saveImage` refuses, `/meta` says `canAnnotate: false`): annotation rewrites `images.data`, which serving would ignore. **Backup**: `ZipWriter.addStream()` writes a stored entry from an async source in two passes (CRC first, since the local header needs it) and `ZipReader.stream()` reads an entry piecewise verifying size + CRC at the end; `files.json` marks such entries `chunked: true` and restore re-chunks them into a pending row that is only finished — or deleted — at the end, so a broken archive never leaves a half file.
- **Files in a 課程筆記 folder are "file notes" (`meta.file = { id, name, mime, size }`).** 課程筆記 (`area: 'course'`, renamed from 證照／課程筆記 — the area key did not change) is the one area whose `areaOpts()` passes `onUploadFile`, which is what makes `js/areabrowser.js` show 上傳檔案, accept a file drop anywhere on the page, and draw a 檔案 section under the notes. An uploaded PPTX/PDF/video is stored through `Store.uploadFile` and then filed as an ordinary note in that folder whose content is just the reference (`![name](img:id)` / `![name](pdf:id)` / `[name](file:id)`) — deliberately not a new table: rename, move, trash/restore, sharing, backup, search and the file library's "used" check (which reads note content) all work with no new code, and a share recipient can stream the file because visibility is already "can read a note that references it". The title is only the display name; the download name stays `meta.file.name`. `openNote()` checks `isFileNote()` on the `state.notes` entry **before** `closeStream()` and opens `openFileViewer()` instead of the editor — a `position: fixed` always-dark overlay (`.fv-*`): PDF in a same-origin `<iframe>`, `<video>`/`<audio>`/`<img>` for exactly the types `INLINE_UPLOAD` serves inline, an uploaded **Markdown** file (`text/markdown` or a `.md`/`.markdown` name) fetched and rendered read-only with `MD.render()` into a `.fv-md.markdown-body` card (same pipeline as the preview, `resolveImages` run after — the server sends `.md` as an octet-stream attachment but a same-origin `fetch` reads its bytes fine; `rawViewable` is false so it gets a 下載 but no 新分頁開啟, which would only download it), and an icon + 下載 for everything else (PPTX, MOV, archives — the server sends those as attachments, so no element could show them). It never sets `state.currentId` or `lastNote`; a `#note/<id>` link to a file lands on its folder in the area page with the viewer on top (`loadData`, `AreaBrowser.openFolder`). Uploads queue in `areabrowser.js` (`uploads`, one at a time, each remembering its own area/folder/callback so switching pages mid-upload still files it correctly) and survive re-renders; a failed one stays as a dismissible error row. When a file note is deleted **for good** (`purgeNote`, `emptyTrash`, the retention sweep) its file goes with it unless another note still references it: `fileOfNoteRow()` reads the id before the note row is deleted, `dropFileIfUnused()` runs after, against the notes that remain — in that order so two trashed notes naming one file cannot keep each other's file alive. Trashing alone never touches the file. File notes are filtered out of 關聯圖's input, and folder tiles count them separately (`N 筆記・M 檔案・K 便條紙`). **An image file shows itself**: `attachThumb()` lays a 40 px `object-fit: cover` thumbnail over the type icon (negative vertical margins keep the row at the same 46 px as every other file row), only once it has actually loaded (`.has-thumb`) — a type the server sends as an attachment (HEIC, TIFF) or a corrupt file fails to decode, the box shrinks back to the ordinary icon, and that id is remembered as `null` in `thumbCache` so re-renders don't refetch it. There is no server-side thumbnailing (one dependency, no image library): like 檔案管理 it loads `/api/images/<id>` with `loading=lazy`, and because those responses are `no-cache` the `<img>` element itself is cached per file id and re-parented on every `render()`, so an upload finishing or a rename never reloads or flashes the thumbnails. Hovering the thumbnail floats a larger preview (`.ab-thumb-pop`, a `position: fixed` body child with `pointer-events: none`, sized from the image's natural proportions) **below** the row, or above when there is no room — beside the thumbnail it covered the file names, including the hovered row's own; it is skipped on non-hover devices and for images already ≤ 80 px, and `render()`, scrolling and opening the viewer all dismiss it.
- **Sticky notes / 便條紙 in 課程筆記 (`meta.sticky = { color }`, `makeSticky` in `js/areabrowser.js`).** The same "special note" trick as file notes: a sticky is an ordinary course note whose `content` is the text on the card, so trash, restore, search, backup and versions need nothing new. 便條紙 in the folder header (`onNewSticky`, course only) creates one and focuses it; the wall sits at the top of the folder page, ordered by creation (by last edit, cards would jump while typing). A card has no view/edit states — it is a `textarea` all the time: each `input` writes `note.content` locally at once and schedules a 600 ms save, blur flushes, and the timers live in a module `Map` keyed by note id rather than on the card, because anything can re-render the page mid-sentence (an upload finishing next to it): `render()` remembers which sticky had focus and its selection and puts them back (`focusSticky`). `onSaveSticky` (`app.js`) sets the title to the first line (`stickyTitle`) only so the trash, search and other title lists can tell stickies apart — the card never shows a title. It writes a colour change into the local `note.meta` *before* the request, and on the reply copies back only `title`/`rev`/`updatedAt`, never `content`/`meta`: the user may have typed or recoloured again meanwhile, and a stale meta sent by the next keystroke's save would otherwise undo the colour. Colours are Windows Sticky Notes' six (pale paper with a darker band in light; a dark card with a saturated band in dark, which is also what Windows does); the band's swatches and move/delete appear on hover or focus. Stickies never open the editor: `openNote()` and `loadData` send a sticky to `goToSticky()` (its area page and folder, caret on the card), and they are kept out of the tree and 關聯圖.
- **匯入 .md imports where you are (`importMarkdownFiles`/`importTarget` in `app.js`).** The sidebar's 匯入 .md opens a menu — 匯入 .md 檔案（可多選） (`#import-input multiple`) or 匯入整個資料夾 (`#import-dir-input webkitdirectory`) — whose last, disabled line (`.ctx-hint`) names the destination. The destination is the same rule as the sidebar's 新增: `currentFolderId()` (an area page's browsed folder, the dashboard's, or the open book's) and `areaForNew()`, plus 隨筆 when its page is showing; it used to be 所有筆記's top level always, so anything imported inside an area had to be moved afterwards. A folder import rebuilds the chosen folder's tree under the destination from each file's `webkitRelativePath` (`ensureDir`, only the levels that actually hold a `.md`; a folder that fails to create sends its notes one level up rather than losing them) and flattens into 隨筆, which has no folders. Notes are created one at a time in path order with their content in the create request. A single plain file still opens straight away (Back then lands on its folder via `anchorBackToFolder`); several files or a folder stay on the page and end in one toast. `DOM.setFileInputFiles` fills a `webkitdirectory` input only when given the *directory* path — passing its files leaves it empty.
- **The images in an imported .md come with it (`js/mdimport.js`, shared by the browser and `server/tools/import-md.js`).** A `.md` from outside references pictures in three ways the site cannot use as they are — a relative path (`![](images/x.png)`: no such file on the site), an external URL (the CSP allows same-origin images only) and `<img src>` (never goes through the image renderer) — plus inline `data:` base64, which would otherwise sit in the note body as tens of KB of noise. `MdImport.scan(text)` returns every reference (`{target, kind: local|remote|data|other, alt, embed, start, end, syntax: link|refdef|html}`) and `MdImport.rewrite(text, resolve)` swaps in the site's own form (`![名稱](img:<id>)` / `![名稱](pdf:<id>)` / `[名稱](file:<id>)`, via `siteRef`) for whatever `resolve` returns an id for — **anything it returns `null` for is left exactly as it was**, which is what makes a missing file or an unfetchable URL a degraded import rather than a broken one. Three parsing details are load-bearing: fenced and indented code is excluded (`codeLines`), so a tutorial that *shows* `![x](images/cover.png)` keeps showing it; reference definitions (`[s1]: guide/img/step 1.png`) take the rest of the line minus a trailing title rather than stopping at the first space, because exported files routinely have spaces in filenames; and a destination with a raw space inside `()` — which marked itself does not accept as a link — is picked up by a second, looser pass (`LOOSE`) that only fires when the path resolves to a file actually in the import, turning an already-broken reference into a working image instead of risking a false positive. The two callers differ in exactly one way, and deliberately: the CLI downloads external images itself (on the user's own machine — **the server must never fetch a user-supplied URL**, see `linkpreview.js` for what that costs when it has to), while the browser leaves them as links and says so in the toast. Everything else is shared, so both surfaces upload one picture once however many notes reference it (`usedAssets`/`wantLocal`), resolve `./`, `../` and `%20` through `resolvePath`, take the note title from YAML front matter or the first heading (`frontMatter`, which also strips the YAML), and only import files nothing references when the target is 課程筆記, where they become ordinary `meta.file` file notes. In `app.js` the phases must stay in this order and inside the scan's `.then` — read+scan every file, *then* upload the referenced assets, *then* create the notes: building the upload/create chain outside that callback silently produced zero notes, because `usedAssets` and `docs` were still empty when `forEach` ran over them.
- **Link preview cards (`{%preview https://… %}`, `server/linkpreview.js`):** a block extension (`linkCardExtension`) renders only a frame with the address; `MD.resolveLinkCards` (called from `resolveImages`, and awaited by `inlineImagesAsDataURL` for PDF/book, which also inlines the thumbnail) fills title/description/image from `GET /api/link-preview`, with `textContent` only. The server fetch is the one place this server connects where a user points it, so it is guarded end to end: http/https on 80/443, no credentials, IP literals checked up front, hostnames resolved through `safeLookup` (passed as the request's `lookup`, so the check and the connection use the same answer) which refuses the whole answer if any address is loopback/private/link-local/CGNAT/metadata/multicast (IPv4-mapped, NAT64 and 6to4 unwrapped), every redirect re-checked, one deadline, a byte cap after decompression, `agent: false`. Images are proxied (`/api/link-preview/image`, raster types only) because the CSP allows only same-origin images and hot-linking would leak viewers' IPs. `LINK_PREVIEW=0` turns the fetch off; cards then show the address. `smoke.js` has a list of addresses that must be refused.
- **Embed switch (`js/embedswitch.js`):** hovering an embedded PDF, a PDF file link, a link card or a web link that is its paragraph's only content shows one floating 「檔案｜預覽」/「連結｜預覽卡片」 bar (a `position: fixed` body child). It is deliberately not in the rendered HTML, so exports never contain it. A click rewrites the source with `MD.switchEmbed(text, start, end, spec)`, limited to the hovered block's source lines, which the host supplies: the preview uses LineSync's `data-line0/1` (so `.link-card` is a coarse `quote` range in `linesync.js`). The last PDF choice is remembered (`localStorage` `pdfDisplay`) for the next upload.
- **Sort order (`js/sorting.js`, `PUT /api/order`):** the sidebar tree and the dashboard share one mode (`localStorage` `sortMode`: manual / name / created / updated) and one comparator. Manual order is `notes.position` / `folders.position`; a never-dragged row is `NULL` and sorts ahead of positioned ones (notes by last update, folders by name), which is exactly the order both lists had before this existed, so nothing moves until something is dragged. Pinned notes are first in every mode. A drop always sends the *whole* level in its new order (`api.js:saveOrder`, which also moves listed rows into that level and refuses a folder into its own subtree), via `placeItems` in `app.js`; dropping between rows in a non-manual mode switches to manual starting from the order on screen, while a plain move into a folder appends to that folder's manual order. `placeItems` also updates `state.current` when it is a different object from the `state.notes` entry — autosave sends `folderId`, and a stale one moves the note straight back. Book chapters still sort by title (`book.js`), independent of this.
- **Image annotation (`annotate.js`):** shapes are stored as vectors alongside the untouched `original` blob; the flattened `data` blob is what notes and PDFs display. Only the image owner may annotate.
- **Image black frame (`![說明](img:<id>#frame)`):** a report screenshot is usually white-on-white against the page, so an image can be given a thin black border. The flag lives in the markdown as a `#frame` suffix on the reference, not in `note.meta` — so every surface reads one source (preview, PDF, book), and copying the line to another note carries it along. `markdown.js`'s `image` renderer splits the suffix off (`id` is `[\w.-]` only, exactly how `server/api.js`'s `MEDIA_REF` cuts it, so nothing after `#` can leak into the id) and puts `img-framed` on the `<img>`; **the server's image-visibility check is a plain `img:<id>` substring match, which a suffix therefore cannot break — `smoke.js` guards that, because if it ever did break, only a *share recipient* would see it, as 404s on every framed image.** The toggle is a `▢ 黑框` button in the hover row over an image (`.img-tools`, sharing a container with `✎ 標註` so adding a button doesn't mean recomputing each one's `right`); `app.js`'s `toggleImageFrame` counts which `<img data-img-id>` in `#preview` was clicked and hands that index to `MD.toggleImageFrame(text, index)`, which rewrites the Nth `![…](img:…)` in the source — **the preview-index ↔ source-index mapping is the same one `toggleTask` relies on, so it has the same two rules: only `!`-prefixed references count (a plain `[x](img:id)` is an ordinary link, never an `<img>`) and fenced code is skipped (a tutorial that *shows* the syntax must not consume a number).** The write goes through `applyEditorText`, i.e. a synthetic `input` event, so autosave/merge/versions need no special case. `.img-tools` only appears inside `#preview`: the book reader, 隨筆 cards and the file viewer render the same markdown with no editor to write back to. The border is `#000` in light mode and in `pdf.js`'s print stylesheet (the whole point is the printed page); dark mode uses a light border instead, since a black line on a dark canvas reads as "the frame didn't apply".
- **Version history (`server/api.js` + `js/versions.js`):** every text save also writes a row into `note_versions`. Saves by the same author inside `VERSION_COALESCE_MS` (5 min) collapse into the row already open, so the 500 ms autosave produces one row per editing session, not per keystroke. The first ever edit of a note additionally snapshots the *pre-edit* text, labelled `啟用版本歷史前`, with an empty author because nothing recorded who wrote it. Rows with a `label` are user-made or system-pinned milestones: never coalesced, never pruned, and not counted against the `VERSION_KEEP` (60) budget. Restoring snapshots the text it is about to replace first, so a restore is itself undoable. `Versions.openNote` renders the diff with `Merge.diffLines`, the same LCS the collaborative merge uses.
- **E-book versions:** a book is a folder, so there is nothing about the book itself to version. A `book_versions` row stores a manifest — the ordered `[{noteId, title, versionId, rev}]` — and pins each chapter to a note version labelled `電子書版本` so pruning cannot delete the text it points at. **Chapter order comes from the client**, because the ordering rule (natural sort of titles) lives in `js/book.js` and must not be reimplemented in SQL. Deleting a book version releases the note versions no surviving book version still references.
- **To-do items:** `markdown.js` overrides marked's `checkbox`/`listitem` to emit an enabled `<input class="task-check" data-task="N">` where N is the checkbox's position in document order (`taskSeq`, reset per render). Both export paths (`pdf.js`, `book.js`) disable these inputs, because outside the editor there is nothing to write back to. A task item's checkbox is `position: absolute` in a padded `li`, not a flex item: LineSync wraps the item's text *and* its checkbox into one `.sync-ln` span, so under flex a long item's second line wrapped back under the checkbox. `pdf.js` restates the same layout for print.

- **Mind maps (`mindmap.js`):** a ` ```mindmap ` fence holding an indented outline. The outline is the source of truth — searchable, mergeable, and readable as plain text — and the SVG is derived on every render. Layout is deterministic and DOM-free (text width is estimated from character classes) so the same picture comes out on screen, in print and in a published file. - **Relationship analysis / 關聯分析 (`js/relmap.js`):** the freeform sibling of mind maps — any node can connect to any other, so unlike a mindmap's outline the layout can't be re-derived from structure alone; a ` ```relmap ` fence's DSL (`node <id> "<label>" x=<n> y=<n> [color=<name>]` / `edge <from> <to> ["<label>"]`, one entry per line, tokenized respecting `"quoted labels"`) is still the source of truth, but it has to carry each node's position explicitly. - **Public e-book share links (`/s/<token>`, `server/db.js` table `book_links`):** the one route in this server that answers with no session at all. It is deliberately a *snapshot*, not a live view — `Book.renderStandalone()` packs the whole book into one self-contained HTML string (images already inlined) and the server stores and later re-serves that exact string. Holding the token therefore grants no API access and no visibility into later edits; the owner has to press 更新內容 to re-pack and overwrite the stored HTML at the same URL. `server.js:serveSharedBook` answers with its own response headers, not `securityHeaders()` — a much stricter CSP (`default-src 'none'`, no `connect-src` at all, so the shared page cannot fetch anything even same-origin) and `noindex`. - **Dashboard drag-and-drop:** `js/dashboard.js` implements it independently of the sidebar tree's own drag-and-drop in `js/app.js` — different DOM and different code, but they must speak **one drag protocol**: two private MIME types, `application/x-strikenote-notes` (a JSON array of note ids) and `application/x-strikenote-folder` (one folder id), plus a `text/plain` fallback, all set on `dragstart` by both surfaces. Each side prefers its own module var (`dragging`/`draggingFolder` in `dashboard.js`, `dragData` in `app.js`) and falls back to the drag's own data — `dragKind(e)` reads `dataTransfer.types` during dragover (the ids are not readable until drop) and `dragPayload(e)` reads the ids on drop. Both halves are load-bearing, because the sidebar is a drawer floating *over* the dashboard: tree rows and folder tiles are on screen together, so dragging a note from the list onto a folder tile (or the reverse) is an obvious gesture, and it is the *other* surface's handlers that have to recognise the drag. The tree's `dragstart` originally set no data at all, which made every such cross-surface drag die silently — `dragover` fired on the tile, nothing called `preventDefault()`, so no `drop` event was ever generated and the note just sprang back. Note that an in-page drag can look completely fine while this is broken: a synthetic `DragEvent` carrying a hand-made `DataTransfer` exercises only the handlers, never Chrome's data store, and Chrome is lenient enough to *start* a drag with an empty one (Firefox is not, so it broke there outright). Reproduce it with `Input.setInterceptDrags` + a real `Input.dispatchMouseEvent` press, which reports the drag's actual items. Dragging a selected note moves the whole checkbox selection, not just the one dragged. The breadcrumb (`renderHead`'s `nav`) is itself a drop target at every level, including 所有筆記 — that is how a note gets dragged back out of a folder to the top level. `onMoveNotes` in `dashOpts()` (`js/app.js`) does the actual `Store.updateNote` calls.

- **Relationship graph (`graph.js`):** an Obsidian-style force-directed graph of `[[wikilink]]` backlinks and `#hashtag` membership across every note. **It is a full page (`#graph-wrap`, `openGraphPage()`/`closeGraphView()` in `app.js`), not a dialog** — the same "take over `#main`" pattern as 垃圾桶/區域頁/關聯分析, so `closeGraphView()` has to sit beside every `closeRelMapView()` call. It was a `.graph-overlay` backdrop with a fixed-size window centred on it, which is a second, smaller screen stacked on an app that already fills the screen: the border and the surrounding gutter ate the area the graph needed. `Graph.open(notes, {container, …})` renders into the container app.js owns and never removes it; `close()` is pure teardown (cancel the rAF, drop the listeners, empty the container) and deliberately does **not** call back, while 返回/Esc go through `opts.onClose` — that split is what keeps 返回 → `showEmpty()` → `closeGraphView()` → `close()` from re-entering. **返回 goes back to wherever you came from**: `openGraphPage()` captures `state.currentId` *before* `leaveOtherViews()` (which nulls it) and `onClose` reopens that note, falling back to the dashboard only when there was no open note or it has since disappeared — opening the graph from a note and being dumped on the dashboard loses your place. The 顯示名稱 checkbox toggles a `hide-labels` class on the canvas, which is purely CSS (`opacity` on `.graph-node-label`) — no DOM rebuild, no re-simulation, since nothing moves; the choice persists in `localStorage` `graphLabels` (app.js owns the storage and passes `showLabels`/`onLabels` in, so graph.js stays storage-free). Unticking it hides every name at once and hovering still reveals one, which is how you read structure on a dense graph; this replaced an automatic "only label nodes with above-average degree" rule, whose `is-minor` class is gone. Reached from the sidebar's 關聯圖 button and from the preview minimap's expand button; deliberately not on the dashboard, so it stays a separate "explore" surface.
- **The preview's corner minimap (`#graph-mini`, `Graph.mini`):** a small card pinned to the top-right of `.pane-preview` showing just the open note's *local* graph — itself in the middle, its direct `[[links]]`, backlinks and `#tags` on one ring. The preview's TOC rail is on the *left*, so the top-right corner is free and the two never collide. **The layout is radial, not the force simulation**: physics inside a 208px box is a clump of jitter that lands somewhere different every repaint, whereas a ring is a pure function of the data, so the same note always draws the same picture. A note with no links or tags still draws **itself**, alone in the middle, rather than a line of explanatory text — "here is this note on the graph, it just hasn't connected to anything yet" is the same picture that grows edges the moment it does. **The viewBox has a floor of the one-ring size** (`Math.max(r + pad, MINI_R + pad)`): a viewBox is a coordinate *range*, so a smaller one scales its contents *up*, and with no neighbours the range shrank to the single dot — which SVG then blew up to fill the whole card, one enormous circle under one enormous label. Flooring it also means a note's dot doesn't change size the moment it gains its first link. It is built from the *live* editor text and title for the open note rather than the `state.notes` copy — that copy only catches up after the autosave round-trip, which made a freshly typed `[[link]]` show up half a second late — while every other note is still the usual snapshot. `syncGraphMini()` runs from `renderPreviewNow()` and `setMode()` but only redraws when the note's own link/tag signature actually changed, so ordinary typing costs one string compare. It hides itself in 編輯-only mode (no preview to sit in) and on narrow screens (the RWD block), and its collapsed state lives in `localStorage` `graphMini`. It rebuilds the graph once per open from `MD.extractLinks`/`MD.extractTags` over the in-memory note list (the same functions the editor and dashboard tag chips already use), so it's a snapshot: edits made while the graph is open aren't reflected until it's reopened. The physics (all-pairs repulsion + per-edge spring + weak centering, damped each frame) runs on `requestAnimationFrame` and stops itself once velocities settle below a threshold, waking back up (`kick()`) on drag or on toggling the 顯示標籤 checkbox. A node click only opens the note/tag if the cumulative mouse movement since mousedown stayed under `DRAG_THRESHOLD` — without that, a few stray pixels of movement (real or synthetic, e.g. from browser automation) gets misread as a drag and swallows the click. `fitView()` fits the current bounding box of all visible nodes to the canvas; it fires once automatically the first time the simulation settles (`hasAutoFit`), and again on demand from the 縮放至整張圖 icon button — always against *current* positions, so it also recovers a view the user dragged or zoomed away from. `app.js` passes `state.notes` minus `area === 'quick'` (untitled scraps that never interlink — pure "未命名筆記" noise as isolated dots) and `'novel'` (a deliberately walled-off area); course/knowledge notes stay in. Edges are quadratic-bezier `<path>`s (`curvePath`, bowing left or right by a hash of the edge's own id pair, so the direction is stable across re-renders, not random each time), dashed — long dashes for note links, dots for tag links — with the stroke picked from a palette deliberately weighted toward orange-brown (`EDGE_COLORS` repeats it) so the texture reads as a warm dashed web with a few blue/red/purple accents rather than an even rainbow. **Nodes are small filled dots** (radius 4–9 for a note, by degree; 3.5 for a tag), the way Obsidian draws them — the size is there to say "this note is well connected", so it must not be spent on being a container for something else. They were a white disc with a coloured ring and a line icon inside, and the disc had to be 10–22 across just to fit that icon, which turned the whole graph into a field of plates; the icon is gone (`iconGroup` with it) and a note is told from a tag by colour alone (tags are always `--folder`), with the name under the dot doing the rest. Hover adds a translucent same-colour halo via `stroke` rather than growing the dot, because growing it shoves the surrounding edges around and the whole graph appears to twitch. The header legend uses the same dots, not icons. Ring/icon colour comes from `nodeColor` (hash of the note id, set inline as `stroke`/`color`); tags keep `--folder` via CSS, matching the two icons in the header legend. Labels sit *below* the node with a `paint-order: stroke` halo in the canvas colour so they stay legible over edges. Only nodes with degree above the graph's average get a label by default (`.is-minor` hides it via CSS); hovering any node reuses the existing `is-hover` mechanism to reveal it regardless of degree. A floating top-left cluster (`.graph-zoom-ctrl`, `−`/`+`/縮放至整張圖) and a bottom-right 重置視圖 button sit absolutely positioned over `.graph-canvas`; 重置視圖 is not just `fitView()` again — it clears every node's `x`/`y` and reruns `seedPositions()` + the simulation, undoing manual dragging rather than only re-framing the camera.

- **The login/register screen has its own brand treatment**, unlike every other dialog in the app: `.auth-box` is split into a gradient `.auth-brand` header (the same `logo.png` mask trick as the topbar logo, just bigger) over a plain `.auth-form` body, on top of a very faint radial accent-colour wash (`.auth-screen`'s background). It is the one screen allowed a resting `box-shadow` outside the "only floating layers get shadows" rule, because the whole card *is* the floating layer here. Field icons (`.auth-field-ic`) must come **after** the `<input>` in markup, not before — the CSS lights them up on `:focus` via `input:focus + .auth-field-ic`, a sibling combinator that only looks forward. `js/auth.js`'s `showBackendProblem()` rebuilds `.auth-box`'s innerHTML for the "backend unreachable" state; it re-emits the same `.auth-brand` block by hand, so a markup change here has to be mirrored there. `.auth-error` reads as a callout (left accent bar + tinted background + icon), not plain red text.
- **Markdown tables are a bordered, shadowed unit**, not a grid of independently-bordered cells: `.markdown-body table` itself carries the outer border and `--shadow-sm`. `th` is explicitly `text-align: left` (browsers default `th` to center and `td` to left, which used to visibly mismatch) with a `2px solid var(--border-strong)` rule under the header row, and the zebra stripe is a flat alpha overlay (`rgba(0,0,0,.025)` / `rgba(255,255,255,.035)` in dark) rather than a token swap — two adjacent neutral tokens can end up too close in value to read as different rows, which is exactly what happened in dark mode before this. `js/pdf.js`'s print CSS for `.pdf-content table` mirrors the left-align and header rule (fixed hex colours, same reasoning as the rest of the print palette); `js/book.js` needs no separate fix since it inlines `app.css` verbatim into the published file.
- **Table column widths (`note.meta.tableWidths`) are a legacy, read-only rendering setting.** Markdown has no column-width concept, so the widths (an array indexed by the table's document order; each entry an array of per-column percentages) live in meta, invisible in the source. They are applied to the *rendered DOM* by `MD.applyColWidths(container, widths)` / `MD.setTableCols(table, pct)` (`markdown.js`), which injects a `<colgroup>` and switches only that table to `display:table; table-layout:fixed; width:100%` (marking it `data-colw` so overlong cells wrap) — a table with no stored widths, or a stored entry whose length no longer matches the columns, is left in the default `display:block; width:fit-content` layout. Every render surface calls it on its own container: `renderPreviewNow`/`exportPDF` in `app.js`, `book.js` (both the reader and the standalone export). The only editing UI that ever wrote to `note.meta.tableWidths` was the now-removed Blog mode's column-drag grips; nothing creates or edits this meta any more, but a note that already carries some from before keeps rendering with it, so this stays a read path, not dead code to delete.
- **Responsive layer (the `RWD` block at the end of `app.css`, breakpoints 900px / 640px):** the desktop layout is never changed; narrow-screen rules are layered on top. Below 900px the sidebar drawer overlays the content instead of pushing it (`#app.sidebar-open .dashboard/.trash-page/.quick-page` lose the `--sidebar-w` padding), split view stacks editor over preview 50/50 (`.panes.mode-split { flex-direction: column }`, divider hidden), the preview TOC rail goes, the editor toolbar scrolls horizontally instead of wrapping, and the full-screen editors (graph, mindmap, image library) fill the window. Below 640px dialogs are near-full-width and scroll internally, the book nav collapses (the pager remains), markdown tables scroll horizontally, and a few inputs are forced to 16px so iOS doesn't zoom on focus. `#app` is `100dvh` (falls back to `100vh`). Two JS behaviours go with it in `app.js`: `autoOpenSidebar()` (the pages that open the drawer by default — 首頁/垃圾桶/區域頁 — only do so above 900px) and the drawer's mousedown-outside rule closes it on any tap into `#main`/`#topbar` when the viewport is ≤900px. `quicknotes.js` lays a single full-width column (up to 600px) when two 240px columns don't fit. Test with the scratchpad `cdp.js` harness's `Emulation.setDeviceMetricsOverride` — the extension cannot shrink a maximized Chrome window.
- `vendor/` holds pinned minified copies of marked, DOMPurify, highlight.js (+ powershell, dos grammars, github light/dark themes that `app.js` swaps on theme change), paged.js, React 18 + ReactDOM 18 + `@xyflow/react` 12 under `vendor/reactflow/` (loaded only by the 關聯分析 page), and the webfonts (`vendor/fonts/`: Inter and Noto Sans TC subsets behind `fonts.css`). There is no CDN usage.
