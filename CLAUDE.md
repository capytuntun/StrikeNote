# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

StrikeNote (folder name `report_system`, UI title 報告筆記系統): a self-hosted, HackMD-style Markdown note app for pentest/exam reporting. It generates OSCP / OSEP / CPENT-LPT / VHL report templates and two structured Taiwanese "資安院" report modes, and exports paginated PDFs. UI strings and most comments are Traditional Chinese.

## Running

There is no build step, no linter, and no unit-test suite. The front-end is plain static files served by the Node server; a front-end change only needs a browser refresh. The server has exactly one npm dependency, `mysql2` (`npm ci`); the database is **MariaDB** (10.11+).

```
npm ci
node server/server.js                                            # http://localhost:8080
node server/tools/smoke.js                                       # end-to-end API exercise against a SCRATCH server
node server/tools/migrate-sqlite-to-mariadb.js --sqlite data.db  # one-shot import of a pre-MariaDB SQLite file
```

Requires Node 22+. Runtime settings are env vars only, read in `server/config.js`: `PORT`, `HOST`, `DB_HOST`/`DB_PORT`/`DB_SOCKET`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` (the server refuses to start without a password unless a socket is given), `REGISTER_MODE` (open|invite|closed, default invite), `INVITE_CODE`, `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `TRUST_PROXY`, `REQUIRE_HTTPS`, `SESSION_TTL_DAYS`, `MIN_PASSWORD_LENGTH`, `MAX_LOGIN_ATTEMPTS`/`LOGIN_LOCKOUT_MINUTES`, `MAX_BODY_BYTES`, `STORAGE_WARN_MB`/`STORAGE_WARN_PCT`, `TRASH_KEEP_DAYS` (default 30). `deploy/env.example` lists them all with production values. On first start with no admin, a random admin password and (in invite mode) a random invite code are printed once to stdout.

A local MariaDB for development, with the same settings production uses:

```
docker run -d --name strikenote-db -e MARIADB_ROOT_PASSWORD=root -e MARIADB_DATABASE=strikenote \
  -e MARIADB_USER=strikenote -e MARIADB_PASSWORD=dev -p 127.0.0.1:3307:3306 mariadb:10.11 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci --max-allowed-packet=64M
DB_PORT=3307 DB_PASSWORD=dev PORT=8090 REQUIRE_HTTPS=0 REGISTER_MODE=open node server/server.js
```

A scratch instance is a different `DB_NAME` (or a different container), never the production database. The schema is created and additively upgraded by `db.init()` on every start, so an empty database is all a scratch instance needs.

Cache busting: every `<script src="js/x.js?v=N">` and the `app.css?v=N` link in `index.html` carry a version query. Bump the number when you change that file, or browsers keep the old copy.

## HARD RULE: never touch real note data

The production MariaDB database, and the pre-migration SQLite file `server/data/data.db` (plus the `server/data-recovery*/` snapshots) still on this machine, hold the user's real exam reports, which are confidential graded evidence. Do not open, query, read, or write any of them, and do not drive the user's logged-in browser tab: on reload the app auto-opens the last note and any `input` event on `#editor` autosaves to the server within ~500 ms, which has already destroyed a real note once. To reproduce or verify anything, use synthetic data in a throwaway harness (a scratch `DB_NAME`/container as above, or serve the static files from another port with no backend, or call `MD.render(...)` / `PDF.showPreview(...)` directly). `server/tools/smoke.js` builds such a fixture; it must only ever be pointed at a scratch server. The migration tool is likewise only ever run by the user against the real file.

## Architecture

### Server (`server/`, one dependency: `mysql2`)

- `server.js` is the only HTTP entry: hand-rolled router for `/api/*`, static file serving from the repo root through an **allow-list** (`STATIC_ALLOW`: only `index.html`, `app.css`, `logo.png`, `favicon.*`, `js/*.js`, `vendor/**`; everything else — `.git/`, `docs/`, `*.md`, `server/` — is 404), security headers, HTTPS redirect behind a proxy, `/api/health` (DB ping, answered before the redirect so a local curl works), 413/400 for oversize/malformed bodies, `uncaughtException`/`unhandledRejection` → log and exit so the supervisor restarts it. It speaks plain HTTP only; TLS is the proxy's job. With `TRUST_PROXY=1`, "secure" means `X-Forwarded-Proto: https` **or** Cloudflare's `CF-Visitor` says so, the client IP comes from `CF-Connecting-IP` then `X-Forwarded-For`, and HSTS is only sent on responses that were actually secure. Exactly one instance runs: presence/SSE and the login throttle are in-process.
- `db.js` owns the schema (users, sessions, folders, notes, images, shares, note_versions, book_versions, book_links) and every prepared statement in the `q` object, on a `mysql2` pool. `q.<name>.get/all/run` are **async** (`run` resolves to `{insertId, affectedRows}`); `db.init()` creates the tables (`CREATE TABLE IF NOT EXISTS`, one statement per array element) and applies the additive `MIGRATIONS` list via `addColumnIfMissing` (information_schema, not try/catch). `tx(async fn)` checks out a connection, BEGINs, and binds it through `AsyncLocalStorage` so every `q.*` inside the callback runs on it; a nested `tx` joins the outer one. Deadlocks / lock-wait timeouts / a restarting MariaDB are "busy": retried a few times, then surfaced with `err.busy`, which the router maps to HTTP 503 + `Retry-After` and the client store retries. Two rules for `tx` callbacks: nothing that escapes the transaction (hub broadcasts, timers) may run inside — collect and fire after — and the body must be safe to run twice. Text ids/tokens are `utf8mb4_bin`; `username` is case-insensitive (`utf8mb4_unicode_ci`), so `Admin` and `admin` are one account. `LENGTH()` in the storage statements is bytes; the version/link lists use `CHAR_LENGTH()` because the UI shows characters.
- `api.js` holds all business logic. Authorization rule for the whole file: identity comes from the session, never the body. Note permission is `owner` | `edit` | `read` via `permFor()`: an explicit share row wins, otherwise the note's "general access" (`notes.access` = `restricted` | `site`, with `access_perm`) lets any signed-in user in. There is deliberately no anonymous or link-token access. Folders are private and never shared; an image is readable by anyone who can read a note whose content contains `img:<id>` or `pdf:<id>`; admin endpoints (`/api/admin/users`, `/api/admin/storage`) return account metadata, counts and byte sizes only, never note text.
- `updateNote` distinguishes text changes (bump `rev`, broadcast, touch `updated_at`) from bookkeeping changes (folder move, `meta` such as `pinned`), which are written without any of that. Do not reintroduce the old early return that compared only content and title: it silently dropped folder moves. Because the DB is async, two saves for one note can interleave, so every read-merge-write on a note (`updateNote`, `restoreVersion`, `restoreBookVersion`, `createVersion`) re-reads the row with `q.noteByIdForUpdate` **inside** its transaction and computes from that locked copy; the permission check on the plain read before it is only a pre-check. `restoreBookVersion` is one transaction for the whole book, locking chapters in manifest order. The admin "last admin" guards use `countAdminsLocked` inside the transaction for the same reason.
- Low-disk warning: `storageSummary()` uses `fs.statfs` on MariaDB's data directory (`SELECT @@datadir`, cached by `db.init()`, falling back up the path); thresholds are `STORAGE_WARN_MB` / `STORAGE_WARN_PCT`. The server logs it at start and hourly; admins get a banner from `Admin.checkStorage()` on login. `adminStorage()`'s `dbBytes` is InnoDB data+index size from `information_schema.TABLES`. Backups are `deploy/backup.sh` (`mariadb-dump --single-transaction`), not anything in the app.
- **Trash (soft delete):** `DELETE /api/notes/:id` does not delete — it sets `notes.deleted_at` (ms epoch). `permFor()` treats a row with `deleted_at` as non-existent, so every normal route (read, save, versions, shares, image visibility, listings) 404s on a trashed note without each of them having to know; only `GET/DELETE /api/trash`, `DELETE /api/trash/:id` and `POST /api/notes/:id/restore` look at those rows, owner-only. Shares, versions and images stay attached, so restore is a one-column update; `q.restoreNote` also nulls a `folder_id` whose folder was deleted meanwhile, otherwise the note would come back invisible. Hard deletes (`q.deleteNote`, FK cascades) happen only on purge, empty-trash, or the hourly `purgeTrash` sweep in `server.js` after `TRASH_KEEP_DAYS`. The client side is `js/trash.js` (`Trash.open`, from the sidebar's 垃圾桶 button); `app.js`'s "delete" paths just call `Store.deleteNote` and re-word the confirm. Deleting a folder still deletes the folder row outright — only its notes go to the trash.
- `auth.js`: scrypt passwords, sessions stored as SHA-256 of a random token in an HttpOnly SameSite=Strict cookie `rn_session`, per-username+IP login throttling. CSRF is a custom `X-Requested-With` header check on non-GET requests.
- `hub.js`: in-memory Server-Sent Events fan-out per note id (`/api/notes/:id/events`) carrying `update`, `presence`, and `cursor` events. Nothing is persisted.
- `merge.js`: line-based LCS three-way merge. `js/merge.js` is a verbatim browser copy; keep the two identical so client and server converge on the same result.

### Front-end (`index.html` + `js/` + `app.css`, vanilla JS)

Every module is an IIFE that publishes one global (`Icons`, `Store`, `Auth`, `MD`, `Editor`, `Templates`, `EditorHL`, `TableTool`, `OSCP`, `SecReport`, `SecEditor`, `PerfReport`, `Dashboard`, `Annotate`, `PDF`, `Search`, `Admin`, `Migrate`, `Merge`, `Book`, `MindMap`, `Versions`, `Trash`, `Graph`, `App`). Load order in `index.html` matters because later scripts call earlier globals; `app.js` is last and orchestrates everything (tree, view modes, autosave, sharing UI, PDF button, paste/drop upload, book mode entry).

- **The markdown editor is always dark**, in both themes — it is a code surface, and only the preview follows the light/dark toggle. Its colours live in the `--ed-*` tokens defined once on `:root` with no `[data-theme="dark"]` overrides; every rule under `.edit-toolbar` / `.editor-area` / `.cm-*` / `#editor` must use those tokens, never `--bg` / `--text` / `--border`, or the editor will go light-on-dark.
- **The editor's syntax highlighting is a separate overlay (`edithl.js`) laid out independently of the textarea.** `#editor` is `color: transparent`; what you see is `.cm-lines` (one `.cm-row` per source line) drawn behind it, kept in step only by `translateY(-scrollTop)` and by both boxes having identical wrap width and identical row heights. Anything that makes a single `.cm-row` differ from the textarea's 31.5px line (e.g. a row with no line box — an empty `<span>` collapses to the 28px gutter — or a line that wraps at a different width) shifts every row below it, and the caret/selection visibly lands on the "wrong" line a few hundred lines down. Hence: blank lines always get a U+200B so they keep a line box, and `--sbw` is measured live from `ta.offsetWidth - ta.clientWidth` on every render (same trick as `syncMirrorStyle` in `app.js`). To check a note, compare `#editor.scrollHeight` with `.cm-lines`' height — they must agree to within 1px.
- **The app shell must never scroll; only the inner panes do.** `#app` is a fixed-height (`100vh`) flex column — `#topbar` (fixed 52px) then `#app-body` — and `html`, `body`, `#app` and `#app-body` are all `overflow: clip`, **and `body` is `position: relative`**. Both halves are load-bearing. On an element, `clip` (not `hidden`) means "not a scroll container", so a `scrollIntoView`/`focus()` skips `#app`/`#app-body` and walks up to the viewport — but `overflow: clip` on `html` is applied to the *viewport* as `hidden` (css-overflow-3), and `hidden` still allows programmatic scrolling. Measured in Chrome 152: with anything sticking out below the fold, `window.scrollTo` and a preview heading's `scrollIntoView({block:'start'})` (the TOC click in `app.js`) both moved `document.scrollingElement`, the latter by exactly the topbar height. So the real guarantee is that *nothing can ever extend past the viewport*: `body` is positioned so an absolutely-positioned body child is contained by `body`'s clip instead of escaping to the initial containing block and growing the viewport's scrollable overflow. That escape was the actual bug behind three fixes (`0bf3904`, `8a206d3`, this one): the caret-measuring mirror `<div>`s in `js/editor.js` (slash popup) and `js/table.js` (table toolbar) are appended to `body` once and cached, copy the textarea's `height`, and were `position: absolute` with no offsets — from the first `/` onward they sat just below `#app`, ~editor height tall, and the next TOC click scrolled the whole shell up 52px: topbar gone, `body`'s background as a strip under the statusbar (reads as "the footer got bigger"). They are `position: fixed; top:0; left:0` now. Rules: anything appended to `body` must be `position: fixed` (every overlay, popup and toast already is); to check a live page, `document.scrollingElement.scrollHeight` must equal `clientHeight`, and if it doesn't, list `document.body.children` for the one with a height below the fold. Chrome clamps `scrollTop` back to 0 the moment the overflow disappears, so the symptom sticks only while the stray element persists. `#app` is `position: relative` for the same containment reason. Scrolling lives entirely in the inner panes (`#editor`, `.preview-scroll`, `.empty-state`, `.sec-editor-scroll`, `.book-*`).
- **The open-note title is absolutely positioned**, not flex-centred: `.note-title-wrap` (holding `#note-path` + `#note-title`) sits at `left: 50%` of `#topbar`, which — because `.panes` is the same full-bleed width as `#topbar` (the sidebar is a floating drawer that never takes layout space) — lands exactly on the editor/preview divider in split view. Centring it by giving the input `flex:1` and `text-align:center` (the previous approach) does not work: the button clusters on either side of the title are different widths, so the input's own box, and therefore its centred text, sits well left of the true midpoint. The folder prefix and the title read as one string (`測試資料夾\測試筆記`) because the input has no fixed width: `fitNoteTitle()` in `app.js` measures the current value (or placeholder) in a hidden `.note-title-measure` span with the same font and sets `style.width` — it runs on open, on every `input`, on remote/rename title changes and after `document.fonts.ready`. The prefix is a link back: clicking `#note-path` calls `goToFolder(state.current.folderId)`, which goes home and then `Dashboard.openFolder(id)` into that folder. A `.note-title-spacer` element still carries the old `flex:1 1 auto` so the history/share/PDF button cluster on the right keeps its position; the split/edit/preview mode switch itself sits in the left-hand group right after the logo, ahead of that spacer, not with them.
- **Icons:** `icons.js` is the only icon source. Static markup uses `data-icon="name"` placeholders that `Icons.mount()` fills at load; JS-built DOM calls `Icons.svg(name)`. Do not add emoji to the chrome; add a path to the dictionary instead. Square-corner design: the `--r*` radius tokens in `app.css` are deliberately all 0.
- **Dashboard:** `dashboard.js` renders folders as tiles on top and the current level's loose notes as a frameless hover list below (checkbox and the pin / rename / "⋯" actions appear on hover; pinned notes sort first via `meta.pinned`). A folder tile previews at most three notes and then a lone "…"; the full list lives in a `.dash-folder-peek` that is rendered into the tile up front and revealed by CSS `:hover` after a 0.35s intent delay, overlaying the tile's bottom edge (`position:absolute; top:100%`) so the tile never grows and the grid never reflows — the peek is a child of the tile, so moving the mouse into it keeps `:hover` alive. All mutations in `app.js` go through `refreshViews()`, which calls `Dashboard.refresh()` so the page updates in place. Callbacks come from `dashOpts()` in `app.js`.
- **Links:** `#note/<id>` and `#book/<folderId>` are the only routes; `openNote`/`openBook` set them with `replaceState`, `loadData` and `hashchange` honour them, and "複製連結" copies them. Anything else in the hash is ignored.
- **Table of contents:** both the preview-pane TOC (`buildPreviewTOC` in `app.js`) and the inline `[toc]` (`buildInlineTOC` in `markdown.js`) list only h1/h2; h3 sits in a collapsed sub-list behind a toggle. Both share the `tocOpen` set keyed by heading id, cleared when a note opens. The inline version is rebuilt on every keystroke, so `restoreInlineTocState()` re-applies the open class after each render; its toggle is a `<button data-toc>` that must stay in the DOMPurify allow-list.
- **Templates:** `templates.js` owns the insert templates behind the toolbar's 範本 button. 機器 and AD Set are built in (text read from `Editor.snippets`, single source); user templates live in `localStorage` under `strikenote.templates` and are pushed into the editor's `/command` list via `Editor.setExtraSnippets`. `$CURSOR` in a template marks where the caret lands.
- **Book mode (`book.js`):** a folder is a book. Notes sort naturally by title (numeric-aware) as chapters, subfolders become parts. The reader is a GitBook-style three-column view inside `#book-wrap`; "出版 HTML" renders every chapter, inlines images as data URLs, embeds `app.css` plus the highlight.js themes, and downloads one self-contained file whose inline script does hash-based chapter routing. The in-app reader and the export share the same nav/pager/outline builders.

- `store.js` is the only module that talks to `/api`. It keeps the promise shape of the old IndexedDB store; `migrate.js` still imports notes left in that old browser DB.
- **Note kinds are decided by `note.meta`.** Plain markdown notes have no special meta. `meta.secReport` opens the step-based 資安院 editor (`seceditor.js`), `meta.perfReport` opens the table-based 成效報告 editor (`perfreport.js`). Both editors keep structured data in meta and also regenerate `note.content` as markdown (via `SecReport.generate` / `PerfReport.generate`) so search, preview, and PDF work unchanged. Cert templates (`oscp.js`) are one-shot generators that just produce markdown content.
- **Collaboration flow:** `app.js` tracks `_syncRev`/`_syncContent` for the open note and sends them as `baseRev`/`baseContent` on every autosave. The server merges against the current row, bumps `rev`, and broadcasts; the client merges incoming remote updates into the live textarea with the same `merge3`, skipping echoes of its own saves by username.
- **Markdown pipeline (`markdown.js`):** marked (`breaks: true` — HackMD semantics, a source newline is a `<br>`; do not "fix" this back to the CommonMark default, users write one sentence per line and expect the preview to match the editor) + DOMPurify + highlight.js with custom tokenizer extensions for GitHub `> [!NOTE]` callouts, HackMD `:::info` containers (aliased onto the same callout HTML), `RISK:` callouts, `[toc]`, and ` ```lang= ` line-number fences. Images are referenced as `![alt](img:<id>)` and embedded PDFs as `![name](pdf:<id>)`; rendering resolves them through `Store.getImageBlob`, a session-lifetime cache of raw image bytes keyed by id that both the preview (`MD.resolveImages`) and PDF export (`MD.inlineImagesAsDataURL`) share, so an image-heavy note is fetched once total instead of once per surface. `Store.getImage` (blob + `/meta`, for shapes/`canAnnotate`) stays the annotation editor's own call, since it is the only caller that needs metadata; `MD.invalidateImage`/`Store.invalidateImage` drop an id from the cache after annotation rewrites it.
- **PDF export (`pdf.js`):** builds a standalone HTML document (cover, TOC with page numbers, themes, watermark) and paginates it with `vendor/paged.polyfill.js` inside a same-origin iframe written via `document.write`, then prints. The in-app preview and the printed output are the same document.
- **Image annotation (`annotate.js`):** shapes are stored as vectors alongside the untouched `original` blob; the flattened `data` blob is what notes and PDFs display. Only the image owner may annotate.
- **Version history (`server/api.js` + `js/versions.js`):** every text save also writes a row into `note_versions`. Saves by the same author inside `VERSION_COALESCE_MS` (5 min) collapse into the row already open, so the 500 ms autosave produces one row per editing session, not per keystroke. The first ever edit of a note additionally snapshots the *pre-edit* text, labelled `啟用版本歷史前`, with an empty author because nothing recorded who wrote it. Rows with a `label` are user-made or system-pinned milestones: never coalesced, never pruned, and not counted against the `VERSION_KEEP` (60) budget. Restoring snapshots the text it is about to replace first, so a restore is itself undoable. `Versions.openNote` renders the diff with `Merge.diffLines`, the same LCS the collaborative merge uses.
- **E-book versions:** a book is a folder, so there is nothing about the book itself to version. A `book_versions` row stores a manifest — the ordered `[{noteId, title, versionId, rev}]` — and pins each chapter to a note version labelled `電子書版本` so pruning cannot delete the text it points at. **Chapter order comes from the client**, because the ordering rule (natural sort of titles) lives in `js/book.js` and must not be reimplemented in SQL. Deleting a book version releases the note versions no surviving book version still references.
- **To-do items:** `markdown.js` overrides marked's `checkbox`/`listitem` to emit an enabled `<input class="task-check" data-task="N">` where N is the checkbox's position in document order (`taskSeq`, reset per render). Clicking one in the preview finds the Nth `- [ ]` line in the textarea — skipping fenced code — flips it, and fires a synthetic `input` event so autosave and re-render happen through the normal path. Both export paths (`pdf.js`, `book.js`) disable these inputs, because outside the editor there is nothing to write back to.
- **Sub-pages:** a wiki link alone on its own line renders as a `.page-card` block instead of an inline link, which is the Notion distinction between a page mention and a sub-page. The `paragraph` renderer in `markdown.js` does it, so it works identically in the preview, the PDF and the published book. The card keeps the `note-link` class, so the existing click handler still opens it or creates it. Its CSS must out-specify `.markdown-body a.note-link`, hence the `.markdown-body a.page-card` selectors.
- **Mind maps (`mindmap.js`):** a ` ```mindmap ` fence holding an indented outline. The outline is the source of truth — searchable, mergeable, and readable as plain text — and the SVG is derived on every render. Layout is deterministic and DOM-free (text width is estimated from character classes) so the same picture comes out on screen, in print and in a published file. Node fill and label colour come from CSS classes, never inline attributes, which is why `pdf.js` has to restate them for the print document; only the per-branch colour is inline. `MindMap.open()` is the editor: Tab adds a child, Enter a sibling, F2 or typing renames, Space collapses, drag re-parents, and saving writes the outline back into that fence.
- **Public e-book share links (`/s/<token>`, `server/db.js` table `book_links`):** the one route in this server that answers with no session at all. It is deliberately a *snapshot*, not a live view — `Book.renderStandalone()` packs the whole book into one self-contained HTML string (images already inlined) and the server stores and later re-serves that exact string. Holding the token therefore grants no API access and no visibility into later edits; the owner has to press 更新內容 to re-pack and overwrite the stored HTML at the same URL. `server.js:serveSharedBook` answers with its own response headers, not `securityHeaders()` — a much stricter CSP (`default-src 'none'`, no `connect-src` at all, so the shared page cannot fetch anything even same-origin) and `noindex`. Tokens are 32 random bytes; links can expire (`expires_at`, nullable = never) and are revoked by row deletion. `js/versions.js:openBookLinks` is the owner-facing dialog (create / refresh / revoke, per link, from the book toolbar's 分享連結 button).
- **Dashboard drag-and-drop:** `js/dashboard.js` implements it independently of the sidebar tree's own drag-and-drop in `js/app.js` (different DOM, different payload — a private `application/x-strikenote-notes` MIME type carrying an array of note ids, set on `dragstart`). Dragging a selected note moves the whole checkbox selection, not just the one dragged. The breadcrumb (`renderHead`'s `nav`) is itself a drop target at every level, including 所有筆記 — that is how a note gets dragged back out of a folder to the top level. `onMoveNotes` in `dashOpts()` (`js/app.js`) does the actual `Store.updateNote` calls.
- **The dashboard has no separate page title.** `renderHead` in `js/dashboard.js` used to build an `<h1>` above the breadcrumb; that's gone, full stop — the breadcrumb (still its normal small size, `.dash-crumb.is-current` just marking the non-clickable last crumb) is the only "where am I" indicator now.
- **Code blocks always span the full pane width and wrap instead of scrolling.** `.code-block` (and `.markdown-body pre` generally) is `width: 100%` regardless of how short the snippet is — a block sized to its content used to look like a wide empty gutter next to a short command, which read as broken. `.code-lines > li` is `white-space: pre-wrap; overflow-wrap: anywhere` so a line too long for the pane wraps — same as the print output always has (`pdf.js`'s `.code-lines > li` has used `pre-wrap` since line numbers were added), rather than opening a horizontal scrollbar for one line.
- **Relationship graph (`graph.js`):** an Obsidian-style force-directed graph of `[[wikilink]]` backlinks and `#hashtag` membership across every note, opened full-screen from the sidebar's 關聯圖 button — deliberately not on the dashboard, so it stays a separate "explore" surface. It rebuilds the graph once per open from `MD.extractLinks`/`MD.extractTags` over the in-memory note list (the same functions the editor and dashboard tag chips already use), so it's a snapshot: edits made while the graph is open aren't reflected until it's reopened. The physics (all-pairs repulsion + per-edge spring + weak centering, damped each frame) runs on `requestAnimationFrame` and stops itself once velocities settle below a threshold, waking back up (`kick()`) on drag or on toggling the 顯示標籤 checkbox. A node click only opens the note/tag if the cumulative mouse movement since mousedown stayed under `DRAG_THRESHOLD` — without that, a few stray pixels of movement (real or synthetic, e.g. from browser automation) gets misread as a drag and swallows the click. `fitView()` fits the current bounding box of all visible nodes to the canvas; it fires once automatically the first time the simulation settles (`hasAutoFit`), and again on demand from the 置中 button in `.graph-bar` — always against *current* positions, so it also recovers a view the user dragged or zoomed away from.
- **The sidebar's 新增 button is a dropdown**, not five buttons: 筆記 / 證照範本 / 資安院報告 / 成效報告 / 電子書 live inside `#new-dropdown`. The option buttons keep their historical ids (`#new-note`, `#oscp-report`, `#sec-report`, `#perf-report`; 電子書 is `#new-book` → `pickBookFolder`), so their click handlers in `app.js` are untouched — the menu only adds open/close around them (`closeNewMenu` runs on the bubbling click *after* the option's own handler has fired). Everything in it except 電子書 is created inside the folder you are currently in: `currentFolderId()` in `app.js` is the dashboard's browsed folder (`Dashboard.currentFolder()`) or, in the reader, the open book's folder, and `null` (top level) otherwise — an open *note* does not count as being in its folder. The items reuse `.user-menu-item` styling from the account menu. The rows under it (`.sidebar-actions`) are a two-column CSS **grid**, not flex: with `flex: 1 1 0%` a `<button>` counts its own padding+border into the base size before free space is shared, while the `div.new-menu` wrapping 新增 has none, so the two "equal" buttons came out 26px apart and the rows' column lines didn't meet. `1fr 1fr` ignores content; a lone button (關聯圖) spans both with `grid-column: 1 / -1`.
- **E-books section (`folders.is_book`):** the dashboard's top level has its own 電子書 section (before 資料夾) listing every folder flagged `isBook` as a `.dash-book-tile` (`makeBookTile` in `js/dashboard.js`); it renders even when empty, as a pointer to 新增 → 電子書. A folder gets the flag the first time it is opened in the reader (`markBook`, called from `openBook`, so the folder tile's "以電子書閱讀", the 新增 → 電子書 picker and a `#book/<id>` link all count); the ✕ on a book tile calls `onBookRemove` → `unmarkBook` and clears it. The flag is the *only* thing the section reads — clearing it removes nothing else, and `updateFolder` leaves `is_book` alone unless the body carries `isBook`, so a rename or move can't drop a book out of the section. There is no e-book button anywhere else; the folder picker (`pickBookFolder`) is reached only through 新增. Inside a folder that *is* a book, the dashboard header shows 更新到電子書 (`onBookUpdate` → `updateBook` in `app.js`) and nothing for other folders: the reader is always live, so "updating" means re-packing every public share link (`Book.renderStandalone()` → `Store.updateBookLink` for each) with the current content, then opening the reader — that is the one-click version of the reader's per-link 更新內容. `Dashboard.render()` (what `showEmpty`/`goHome` call) resets *both* `tagFilter` and `curFolderId`, so the StrikeNote logo really goes to the top level; `refresh()` keeps them.
- **The login/register screen has its own brand treatment**, unlike every other dialog in the app: `.auth-box` is split into a gradient `.auth-brand` header (the same `logo.png` mask trick as the topbar logo, just bigger) over a plain `.auth-form` body, on top of a very faint radial accent-colour wash (`.auth-screen`'s background). It is the one screen allowed a resting `box-shadow` outside the "only floating layers get shadows" rule, because the whole card *is* the floating layer here. Field icons (`.auth-field-ic`) must come **after** the `<input>` in markup, not before — the CSS lights them up on `:focus` via `input:focus + .auth-field-ic`, a sibling combinator that only looks forward. `js/auth.js`'s `showBackendProblem()` rebuilds `.auth-box`'s innerHTML for the "backend unreachable" state; it re-emits the same `.auth-brand` block by hand, so a markup change here has to be mirrored there. `.auth-error` reads as a callout (left accent bar + tinted background + icon), not plain red text.
- **Markdown tables are a bordered, shadowed unit**, not a grid of independently-bordered cells: `.markdown-body table` itself carries the outer border and `--shadow-sm`. `th` is explicitly `text-align: left` (browsers default `th` to center and `td` to left, which used to visibly mismatch) with a `2px solid var(--border-strong)` rule under the header row, and the zebra stripe is a flat alpha overlay (`rgba(0,0,0,.025)` / `rgba(255,255,255,.035)` in dark) rather than a token swap — two adjacent neutral tokens can end up too close in value to read as different rows, which is exactly what happened in dark mode before this. `js/pdf.js`'s print CSS for `.pdf-content table` mirrors the left-align and header rule (fixed hex colours, same reasoning as the rest of the print palette); `js/book.js` needs no separate fix since it inlines `app.css` verbatim into the published file.
- `vendor/` holds pinned minified copies of marked, DOMPurify, highlight.js (+ powershell, dos grammars), and paged.js. There is no CDN usage.
