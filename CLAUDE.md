# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

StrikeNote (folder name `report_system`, UI title 報告筆記系統): a self-hosted, HackMD-style Markdown note app for pentest/exam reporting. It generates OSCP / OSEP / CPENT-LPT / VHL report templates and two structured Taiwanese "資安院" report modes, and exports paginated PDFs. UI strings and most comments are Traditional Chinese.

## Running

There is no build step, no linter, and no unit-test suite. The front-end is plain static files served by the Node server; a front-end change only needs a browser refresh. The server has exactly one npm dependency, `mysql2` (`npm ci`); the database is **MariaDB** (10.11+).

```
npm ci
node server/server.js                                            # npm start; http://localhost:8080
node server/tools/smoke.js                                       # npm run smoke; end-to-end API exercise against a SCRATCH server
node server/tools/migrate-sqlite-to-mariadb.js --sqlite data.db  # npm run migrate; one-shot import of a pre-MariaDB SQLite file (--dry-run first)
```

Requires Node 22+. Runtime settings are env vars only, read in `server/config.js`: `PORT`, `HOST`, `DB_HOST`/`DB_PORT`/`DB_SOCKET`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` (the server refuses to start without a password unless a socket is given), `REGISTER_MODE` (open|invite|closed, default invite) and `INVITE_CODE` — both only *starting* values: once an admin changes either in 帳號管理 the `settings` table wins (`server/settings.js`), so editing the env afterwards does nothing — `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `TRUST_PROXY`, `REQUIRE_HTTPS`, `SESSION_TTL_DAYS`, `MIN_PASSWORD_LENGTH`, `MAX_LOGIN_ATTEMPTS`/`LOGIN_LOCKOUT_MINUTES`, `MAX_BODY_BYTES`, `STORAGE_WARN_MB`/`STORAGE_WARN_PCT`, `TRASH_KEEP_DAYS` (default 30), `LINK_PREVIEW` (default 1; 0 stops the server fetching pages for link preview cards). `deploy/env.example` lists them all with production values. Production is a Raspberry Pi / Debian host provisioned by `deploy/install.sh` (idempotent: re-running it is also the update path), with settings in `/etc/strikenote/env` and TLS terminated by cloudflared or a reverse proxy; see `deploy/README.md`. On first start with no admin, a random admin password is printed once to stdout; in invite mode with no code yet, a random invite code is generated, stored in `settings` and printed once — after that it is shown (and can be changed or regenerated) in 帳號管理, which is also where an admin switches between 邀請制 / 開放註冊 / 關閉註冊.

A local MariaDB for development, with the same settings production uses:

```
docker run -d --name strikenote-db -e MARIADB_ROOT_PASSWORD=root -e MARIADB_DATABASE=strikenote \
  -e MARIADB_USER=strikenote -e MARIADB_PASSWORD=dev -p 127.0.0.1:3307:3306 mariadb:10.11 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci --max-allowed-packet=64M
DB_PORT=3307 DB_PASSWORD=dev PORT=8090 REQUIRE_HTTPS=0 REGISTER_MODE=open node server/server.js
```

A scratch instance is a different `DB_NAME` (or a different container), never the production database. The schema is created and additively upgraded by `db.init()` on every start, so an empty database is all a scratch instance needs.

`smoke.js` is the closest thing to a test suite: one script run top to bottom (there is no way to run a single section), printing PASS/FAIL per check and exiting 1 on any failure. It targets `BASE_URL` (default `http://127.0.0.1:8090`), logs in as `ADMIN_USERNAME`/`ADMIN_PASSWORD` (default `admin` / `scratchpass123`) and self-registers a second user `bob` with an empty invite code, so start the scratch server with `ADMIN_PASSWORD=scratchpass123 REGISTER_MODE=open` on an empty database. Its body-limit check reads `MAX_BODY_BYTES`, so give both processes the same value. `--old` skips the MariaDB-only checks.

Cache busting: every `<script src="js/x.js?v=N">` and the `app.css?v=N` link in `index.html` carry a version query. Bump the number when you change that file. The server already sends `no-store` for its own `.html`/`.css`/`.js` (only `vendor/` is cacheable, for a day), so the bump is the second line of defence against a proxy or CDN edge in between that holds an old copy; keep doing it.

## HARD RULE: never touch real note data

The production MariaDB database, and the pre-migration SQLite file `server/data/data.db` (plus the `server/data-recovery*/` snapshots) still on this machine, hold the user's real exam reports, which are confidential graded evidence. Do not open, query, read, or write any of them, and do not drive the user's logged-in browser tab: on reload the app auto-opens the last note and any `input` event on `#editor` autosaves to the server within ~500 ms, which has already destroyed a real note once. To reproduce or verify anything, use synthetic data in a throwaway harness (a scratch `DB_NAME`/container as above, or serve the static files from another port with no backend, or call `MD.render(...)` / `PDF.showPreview(...)` directly). `server/tools/smoke.js` builds such a fixture; it must only ever be pointed at a scratch server. The migration tool is likewise only ever run by the user against the real file.

## Architecture

### Server (`server/`, one dependency: `mysql2`)

- `server.js` is the only HTTP entry: hand-rolled router for `/api/*`, static file serving from the repo root through an **allow-list** (`STATIC_ALLOW`: only `index.html`, `app.css`, `logo.png`, `favicon.*`, `js/*.js`, `vendor/**`; everything else — `.git/`, `docs/`, `*.md`, `server/` — is 404), security headers, HTTPS redirect behind a proxy, `/api/health` (DB ping, answered before the redirect so a local curl works), 413/400 for oversize/malformed bodies, `uncaughtException`/`unhandledRejection` → log and exit so the supervisor restarts it. It speaks plain HTTP only; TLS is the proxy's job. `server.keepAliveTimeout` (95 s) deliberately outlasts cloudflared's 90 s reuse of idle upstream connections: at Node's default 5 s the two crossed, and a POST sent down a socket Node was just closing came back as a 502 (the proxy only retries GETs by itself). With `TRUST_PROXY=1`, "secure" means `X-Forwarded-Proto: https` **or** Cloudflare's `CF-Visitor` says so, the client IP comes from `CF-Connecting-IP` then `X-Forwarded-For`, and HSTS is only sent on responses that were actually secure. Exactly one instance runs: presence/SSE and the login throttle are in-process.
- `db.js` owns the schema (users, sessions, folders, notes, images, shares, note_versions, book_versions, book_links, settings) and every prepared statement in the `q` object, on a `mysql2` pool. `q.<name>.get/all/run` are **async** (`run` resolves to `{insertId, affectedRows}`); `db.init()` creates the tables (`CREATE TABLE IF NOT EXISTS`, one statement per array element) and applies the additive `MIGRATIONS` list via `addColumnIfMissing` (information_schema, not try/catch). `tx(async fn)` checks out a connection, BEGINs, and binds it through `AsyncLocalStorage` so every `q.*` inside the callback runs on it; a nested `tx` joins the outer one. Deadlocks / lock-wait timeouts / a restarting MariaDB are "busy": retried a few times, then surfaced with `err.busy`, which the router maps to HTTP 503 + `Retry-After` and the client store retries. Two rules for `tx` callbacks: nothing that escapes the transaction (hub broadcasts, timers) may run inside — collect and fire after — and the body must be safe to run twice. Text ids/tokens are `utf8mb4_bin`; `username` is case-insensitive (`utf8mb4_unicode_ci`), so `Admin` and `admin` are one account. `LENGTH()` in the storage statements is bytes; the version/link lists use `CHAR_LENGTH()` because the UI shows characters.
- `api.js` holds all business logic. Authorization rule for the whole file: identity comes from the session, never the body. Note permission is `owner` | `edit` | `read` via `permFor()`: an explicit share row wins, otherwise the note's "general access" (`notes.access` = `restricted` | `site`, with `access_perm`) lets any signed-in user in. There is deliberately no anonymous or link-token access. Folders are private and never shared; an image is readable by anyone who can read a note whose content contains `img:<id>` or `pdf:<id>`; admin endpoints (`/api/admin/users`, `/api/admin/storage`) return account metadata, counts and byte sizes only, never note text.
- **Areas (`notes.area` / `folders.area`, `server/api.js` `AREAS`/`normalizeArea`):** a note's or folder's home is `NULL` (一般 — the dashboard/sidebar tree exactly as before this existed) or one of `'course'` (證照／課程筆記) / `'knowledge'` (知識區) / `'quick'` (隨筆) / `'novel'` (小說), set at creation — `updateNote`'s SQL has no `area` column, so a normal save can never change it, and `resolveArea()` refuses to create a note/folder whose `area` doesn't match the folder it's filed into (a folder's own area is likewise fixed, checked the same way on every move). Three of the four areas ride along in the *same* `GET /api/notes`/`GET /api/folders` response as general notes (cheap to expose, filtered client-side by `.area` — see the front-end bullet below); `'novel'` is the one excluded even from its own owner by the SQL itself (`notesOwned`/`foldersOf`: `area IS NULL OR area <> 'novel'`) until unlocked. **Moving a note between 所有筆記／證照課程筆記／知識區** (`PUT /api/notes/:id/area` → `moveNoteArea`, `MOVABLE_AREAS = [null, 'course', 'knowledge']`) is the one deliberate way area *does* change after creation — owner-only, validated exactly like `resolveArea` (the target folder, if given, must belong to the target area), and pointedly refuses `'novel'`/`'quick'` on either end: novel stays behind its gate with no back door, and quick notes have no folder concept to land in. It resets `position` to `NULL` (a manual-order slot from the old area's level means nothing in the new one). Reachable from three places that all funnel into the same `js/app.js` `moveNoteToArea()`/`doMoveNoteArea()` — the dashboard's "⋯" menu and the sidebar tree's right-click (both only ever show general notes, so the option is always offered there) and `js/areabrowser.js`'s own row action (wired through `areaOpts().onMoveArea`, offered only when `MOVABLE_AREAS` includes the note's current area) — picking a target area opens `showFolderPicker` scoped to that area's own folders (`o.folders` override), then `refreshViews()` picks the change up everywhere at once since every area's notes/folders are always freshly filtered from `state.notes`/`state.folders`, never cached per-view. **`permFor()` is the single choke point that makes 小說 real protection, not a client-side skin**: `if (note.area === 'novel' && !(owner && novelUnlocked(user))) return null` — the same pattern that already makes a trashed note invisible to every route (versions, images, PDF-via-read, sharing) without each of them special-casing it. `novelUnlocked(user)` checks `user.novelUnlockedAt` (attached onto the user object by `auth.userFromToken` from `sessions.novel_unlocked_at`) is set and fresher than `NOVEL_UNLOCK_TTL_MS` (1 hour). `POST /api/novel/unlock` (`server/auth.js` `unlockNovel`, called from `js/app.js` `promptNovelPassword()`) re-verifies the caller's *own current* password (`auth.verifyPassword`, sharing the login throttle keyed with a `'novel:'` prefix so a wrong novel-password attempt can't lock out real login) and stamps that session's row — **a wrong attempt must answer 403, never 401**: `js/store.js`'s `req()` treats any 401 as "session expired" and force-logs-out via `alert()`, which is the wrong response to a second-factor typo and was live in this codebase once before the fix. A novel note can never be shared or opened site-wide (`setAccess` refuses `area === 'novel'` outright); `js/app.js`'s own `novelIsUnlocked` flag is deliberately never persisted (in-memory only, so every fresh page load re-prompts even if the server-side unlock is still within its hour) — the UX is a per-visit gate, not a per-login-session one. `server/backup.js` round-trips `area` through export/import (`normalizeArea`, re-exported from `api.js`) and refuses to restore a novel note with `access: 'site'` even if the archive claims one.
- `updateNote` distinguishes text changes (bump `rev`, broadcast, touch `updated_at`) from bookkeeping changes (folder move, `meta` such as `pinned`), which are written without any of that. Do not reintroduce the old early return that compared only content and title: it silently dropped folder moves. Because the DB is async, two saves for one note can interleave, so every read-merge-write on a note (`updateNote`, `restoreVersion`, `restoreBookVersion`, `createVersion`) re-reads the row with `q.noteByIdForUpdate` **inside** its transaction and computes from that locked copy; the permission check on the plain read before it is only a pre-check. `restoreBookVersion` is one transaction for the whole book, locking chapters in manifest order. The admin "last admin" guards use `countAdminsLocked` inside the transaction for the same reason.
- Low-disk warning: `storageSummary()` uses `fs.statfs` on MariaDB's data directory (`SELECT @@datadir`, cached by `db.init()`, falling back up the path); thresholds are `STORAGE_WARN_MB` / `STORAGE_WARN_PCT`. The server logs it at start and hourly; admins get a banner from `Admin.checkStorage()` on login. `adminStorage()`'s `dbBytes` is InnoDB data+index size from `information_schema.TABLES`. Backups are `deploy/backup.sh` (`mariadb-dump --single-transaction`), not anything in the app.
- **Backup and restore (`server/backup.js`, `server/zip.js`, `js/backup.js`; 帳號選單 → 備份與還原):** `GET /api/backup?scope=mine|site` streams a zip built by the dependency-free `ZipWriter` (whole entries, real sizes in every local header, UTF-8 names, zip64 only when needed) straight into the response with back-pressure, fetching one note / one image at a time so a big site is never in memory at once. The layout is readable without the app — `notes/<資料夾>/<標題>.md` (trashed under `_垃圾桶/`, site scope under `<username>/`), `files/<id>.<ext>`, `versions/<noteId>/<versionId>.md`, `books/<token>.html` — and the JSON indexes (`folders.json`, `notes.json`, `files.json`, `books.json`, plus `users.json` with scrypt hashes and `settings.json` for `site`) carry ids, timestamps, meta, access, shares and positions. Restore reads only the indexes and the paths they name (`findManifest` tolerates a re-zipped parent directory), so stray entries are ignored. **Restore keeps ids and is idempotent**: missing rows are recreated with their ids and timestamps (`insertNoteFull` etc.), existing rows owned by the caller are skipped unless `overwrite`, which snapshots the current text as a version labelled 還原備份前 first and broadcasts through the hub; an id owned by someone else is a conflict, skipped and reported, never taken over. A `mine` backup always restores into the caller's account; a `site` backup (admin only) maps owners by username, creates missing accounts with their old hashes and keeps existing ones — so the restoring admin's password never changes. Version ids are AUTO_INCREMENT and are remapped into book-version manifests; a book version whose chapters cannot all be resolved is skipped. Uploads come in chunks (`PUT /api/backup/upload/:id?offset=N`, each under `MAX_BODY_BYTES`, refused on an offset mismatch so a retried chunk cannot double-append) into `os.tmpdir()` up to `BACKUP_MAX_BYTES`, then `inspect` returns the manifest for the confirm step and `restore` runs as a background job the client polls — behind a tunnel one request can neither carry 100 MB nor stay open for minutes. One restore runs at a time; temp files and finished jobs are swept after an hour, and leftovers from a crashed process at start.
- **Trash (soft delete):** `DELETE /api/notes/:id` does not delete — it sets `notes.deleted_at` (ms epoch). `permFor()` treats a row with `deleted_at` as non-existent, so every normal route (read, save, versions, shares, image visibility, listings) 404s on a trashed note without each of them having to know; only `GET/DELETE /api/trash`, `DELETE /api/trash/:id` and `POST /api/notes/:id/restore` look at those rows, owner-only. Shares, versions and images stay attached, so restore is a one-column update; `q.restoreNote` also nulls a `folder_id` whose folder was deleted meanwhile, otherwise the note would come back invisible. Hard deletes (`q.deleteNote`, FK cascades) happen only on purge, empty-trash, or the hourly `purgeTrash` sweep in `server.js` after `TRASH_KEEP_DAYS`. The client side is a full page, not a dialog: `openTrash()` in `app.js` (the sidebar's 垃圾桶 row, or `#trash`) hides the other views and shows `#trash-wrap`, and `Trash.render(container, opts)` in `js/trash.js` draws a dashboard-style page into it (breadcrumb head, a separate section for notes within 3 days of purge, per-row and checkbox-batch restore/purge, search, 清空垃圾桶). `showEmpty`/`openNote`/`openBook` hide it again. Like the dashboard it keeps the sidebar drawer open (`openTrash` opens it, and the click-outside rule in `initSidebarDrawer` skips both views), and `refreshViews()` re-renders it while it is visible so a note deleted from the sidebar appears without a reload. `app.js`'s "delete" paths just call `Store.deleteNote` and re-word the confirm. Deleting a folder still deletes the folder row outright — only its notes go to the trash.
- `auth.js`: scrypt passwords, sessions stored as SHA-256 of a random token in an HttpOnly SameSite=Strict cookie `rn_session`, per-username+IP login throttling. CSRF is a custom `X-Requested-With` header check on non-GET requests.
- `hub.js`: in-memory Server-Sent Events fan-out per note id (`/api/notes/:id/events`) carrying `update`, `presence`, and `cursor` events. Nothing is persisted.
- `merge.js`: line-based LCS three-way merge. `js/merge.js` is the browser copy: `merge3` and its helpers (`lcsPairs`, `diffHunks`, `overlaps`) must stay identical in logic so client and server converge on the same result. The files themselves are not byte-identical (IIFE publishing `window.Merge` vs `module.exports`, different comments, and `diffLines`/`diffStat` are browser-only additions for the version viewer), so compare the functions, not the files. `overlaps()` must treat two insertions (zero-width hunks, `s === e`) at the *same* base position as conflicting, not just genuinely-overlapping ranges — that case was missing once, and a same-point insertion is one merge3 already produces on every save when `baseContent` is stale (a note reopened elsewhere, or a client behind by more than one save): the ancestor is treated as "insert everything," so both sides' insertions land at the same anchor and, without that check, both got kept side by side. Harmless-looking on its own, but a *repeated* stale-base save (multiple tabs/collaborators on one note, or any client whose `_syncContent` has fallen behind) re-embeds the other side's entire already-merged text as one more same-point insertion each time — confirmed by load-testing a scratch server: 50 concurrent saves to one note inflated it from ~15 KB to 1.5 MB and pushed the median latency for that burst from 365 ms to 8.7 s, because the LCS table (`lcsPairs`) is O(lines²) and the row stays locked (`noteByIdForUpdate` is `SELECT ... FOR UPDATE`) for the length of that merge — so a single bloated note can make concurrent access to it feel across-the-board slow, not just to that note.

### Front-end (`index.html` + `js/` + `app.css`, vanilla JS)

Every module is an IIFE that publishes one global (`Icons`, `Store`, `Auth`, `MD`, `Editor`, `Templates`, `EditorHL`, `TableTool`, `OSCP`, `SecReport`, `SecEditor`, `PerfReport`, `Dashboard`, `Annotate`, `PDF`, `Search`, `Admin`, `Migrate`, `Merge`, `Book`, `MindMap`, `Versions`, `Trash`, `ImageLib`, `Graph`, `LineSync`, `BlogMode`, `App`). Load order in `index.html` matters because later scripts call earlier globals; `app.js` is last and orchestrates everything (tree, view modes, autosave, sharing UI, PDF button, paste/drop upload, book mode entry).

- **The markdown editor is always dark**, in both themes — it is a code surface, and only the preview follows the light/dark toggle. Its colours live in the `--ed-*` tokens defined once on `:root` with no `[data-theme="dark"]` overrides; every rule under `.edit-toolbar` / `.editor-area` / `.cm-*` / `#editor` must use those tokens, never `--bg` / `--text` / `--border`, or the editor will go light-on-dark.
- **The editor's syntax highlighting is a separate overlay (`edithl.js`) laid out independently of the textarea.** `#editor` is `color: transparent`; what you see is `.cm-lines` (one `.cm-row` per source line) drawn behind it, kept in step only by `translateY(-scrollTop)` and by both boxes having identical wrap width and identical row heights. Anything that makes a single `.cm-row` differ from the textarea's 31.5px line (e.g. a row with no line box — an empty `<span>` collapses to the 28px gutter — or a line that wraps at a different width) shifts every row below it, and the caret/selection visibly lands on the "wrong" line a few hundred lines down. Hence: blank lines always get a U+200B so they keep a line box, and `--sbw` is measured live from `ta.offsetWidth - ta.clientWidth` on every render (same trick as `syncMirrorStyle` in `app.js`). To check a note, compare `#editor.scrollHeight` with `.cm-lines`' height — they must agree to within 1px.
- **The app shell must never scroll; only the inner panes do.** `#app` is a fixed-height (`100vh`) flex column — `#topbar` (fixed 52px) then `#app-body` — and `html`, `body`, `#app` and `#app-body` are all `overflow: clip`, **and `body` is `position: relative`**. Both halves are load-bearing. On an element, `clip` (not `hidden`) means "not a scroll container", so a `scrollIntoView`/`focus()` skips `#app`/`#app-body` and walks up to the viewport — but `overflow: clip` on `html` is applied to the *viewport* as `hidden` (css-overflow-3), and `hidden` still allows programmatic scrolling. Measured in Chrome 152: with anything sticking out below the fold, `window.scrollTo` and a preview heading's `scrollIntoView({block:'start'})` (the TOC click in `app.js`) both moved `document.scrollingElement`, the latter by exactly the topbar height. So the real guarantee is that *nothing can ever extend past the viewport*: `body` is positioned so an absolutely-positioned body child is contained by `body`'s clip instead of escaping to the initial containing block and growing the viewport's scrollable overflow. That escape was the actual bug behind three fixes (`0bf3904`, `8a206d3`, this one): the caret-measuring mirror `<div>`s in `js/editor.js` (slash popup) and `js/table.js` (table toolbar) are appended to `body` once and cached, copy the textarea's `height`, and were `position: absolute` with no offsets — from the first `/` onward they sat just below `#app`, ~editor height tall, and the next TOC click scrolled the whole shell up 52px: topbar gone, `body`'s background as a strip under the statusbar (reads as "the footer got bigger"). They are `position: fixed; top:0; left:0` now. Rules: anything appended to `body` must be `position: fixed` (every overlay, popup and toast already is); to check a live page, `document.scrollingElement.scrollHeight` must equal `clientHeight`, and if it doesn't, list `document.body.children` for the one with a height below the fold. Chrome clamps `scrollTop` back to 0 the moment the overflow disappears, so the symptom sticks only while the stray element persists. `#app` is `position: relative` for the same containment reason. Scrolling lives entirely in the inner panes (`#editor`, `.preview-scroll`, `.empty-state`, `.trash-wrap`, `.sec-editor-scroll`, `.book-*`).
- **The topbar collapses progressively as it runs out of room (`fitTopbar()` in `app.js`),** not at viewport breakpoints: it measures whether the absolutely-positioned title actually collides with the mode-switch or the right-hand buttons — and, once the title is hidden, whether `#topbar` itself still overflows — and escalates through `topbar-lvl1`…`topbar-lvl5` on `#topbar` until it fits, re-checking after each step so it also relaxes back down when there's room again. Measuring beats a fixed `@media` width because what actually matters is the topbar's own content width, which changes with the note title's length and with how many mode buttons exist (adding Blog mode's button was what first made this collide at widths that used to be fine — a title-width-only check doesn't see a mode-switch that's grown wider). Called from `fitNoteTitle()`, on window resize, and from a `ResizeObserver` on `#topbar`. Each level hides one more thing, least-costly first: lvl1 the capybara/presence (pure decoration); then, before any label goes, `capTitle()` narrows `.note-title-wrap` (inline `max-width`, down to `TITLE_MIN` 240px) to the room between the mid-line and the nearer button cluster, so a long folder path is cut to `…/` instead — without that step a note in a deeply named folder lost every button label at an ordinary 1500px laptop width; lvl2 the mode-switch and 版本/分享/PDF button labels (icons only), after which `capTitle()` runs again with the room that freed; lvl3 the title itself (and the now-pointless 80px title spacer, which is `min-width` load-bearing only while the title needs balancing) — checking `visibility:hidden` here matters, else the hidden title's stale position keeps failing the fit check forever; lvl4 collapses 版本/分享/PDF into one `#topbar-more-btn` (its handler must `stopPropagation()`, same as every other `openMenuAt` trigger, or the same click's bubble to `document`'s `hideCtx` closes the menu it just opened) and drops the username text; lvl5 drops the `StrikeNote` wordmark, keeping the mark. Split view itself stays a flat 50/50 below that — an editor and preview pane both need real width, and 編輯/預覽-only remain the user's own way out at that point.
- **The open-note title is absolutely positioned**, not flex-centred: `.note-title-wrap` (holding `#note-path` + `#note-title`) sits at `left: 50%` of `#topbar`, which — because `.panes` is the same full-bleed width as `#topbar` (the sidebar is a floating drawer that never takes layout space) — lands exactly on the editor/preview divider in split view. Centring it by giving the input `flex:1` and `text-align:center` (the previous approach) does not work: the button clusters on either side of the title are different widths, so the input's own box, and therefore its centred text, sits well left of the true midpoint. The folder prefix and the title read as one string (`測試資料夾/測試筆記`; nested folders as `上層/下層/筆記`, built by `folderPath`; `updateNotePath` puts the path and the `/` in separate spans so an over-long path truncates without hiding the `/` — never cap `.note-path-text` with a percentage: the wrap is sized by its content, so a % resolves against path + title and a short title got a roomy folder name cut to `specterops_tr…`) because the input has no fixed width: `fitNoteTitle()` in `app.js` measures the current value (or placeholder) in a hidden `.note-title-measure` span with the same font and sets `style.width` — it runs on open, on every `input`, on remote/rename title changes and after `document.fonts.ready`. The prefix is a link back: clicking `#note-path` calls `goToFolder(state.current.folderId)`, which goes home and then `Dashboard.openFolder(id)` into that folder. A `.note-title-spacer` element still carries the old `flex:1 1 auto` so the history/share/PDF button cluster on the right keeps its position; the split/edit/preview mode switch itself sits in the left-hand group right after the logo, ahead of that spacer, not with them.
- **Icons:** `icons.js` is the only icon source. Static markup uses `data-icon="name"` placeholders that `Icons.mount()` fills at load; JS-built DOM calls `Icons.svg(name)`. Do not add emoji to the chrome; add a path to the dictionary instead. Square-corner design: the `--r*` radius tokens in `app.css` are deliberately all 0.
- **Dashboard:** `dashboard.js` renders folders as tiles on top and the current level's loose notes as a frameless hover list below (checkbox and the pin / rename / "⋯" actions appear on hover; pinned notes sort first via `meta.pinned`). Inline marks toggle by counting the marker run on each side, so `*` (odd count) vs `**` (≥2) never corrupt each other (bold+italic is `**`→`***`). The `.blog-fmt`, `.ac-popup`, `.wyg-slash`, `.wyg-fmt` and `.tg-menu` are excluded from `onDocDown` so clicking any of these floating panels does not end the edit. Blocks render separately, so RISK numbering and heading anchors are per block in this view (`[toc]` alone is rendered from the whole note).
- **Blog's WYSIWYG prose editing (`js/blogwyg.js`).** A heading/paragraph/list/quote block in Blog is edited the way Notion does it — directly on the rendered element (`contenteditable="true"` on the `.blog-block`'s `h1..h6`/`p`/`ul`/`ol`/`blockquote`), never showing `#`, `>`, `-`, `**`. Typing `/` opens a type-picker (內文/H1–H3/清單/編號清單/待辦/引言/程式碼/表格/分隔線); selecting text floats a Notion-style bubble (`.wyg-fmt`) for bold/italic/strike/inline-code/link plus block-type buttons (list has no block-type buttons — several items have no single equivalent type). Every DOM mutation re-serialises the whole block to Markdown (`BlogWyg.serialize`) and blogmode splices just that block's lines back into `#editor`'s value — same write path, same autosave/merge/search/PDF/versions guarantee as the textarea fallback. **Safety gate (`BlogWyg.canEdit`), the one rule that must never be loosened:** a block only gets WYSIWYG if rendering its Markdown, serialising that DOM back, and rendering the result *again* produces byte-identical HTML (`normHtml` diff) to the first render — proven this way because a wrong serialiser silently corrupts a real report on save, and this is the one guard standing between it and that. Anything the serialiser doesn't (yet) cover — code, tables, callouts/`:::`/`RISK:`, mindmaps, images, `[toc]`, raw HTML — fails the gate and falls back to the plain textarea exactly as before; the gate is checked by kind *and* by the actual rendered HTML (`el.querySelector('.callout, .md-risk, table, pre, img, .link-card, .mm-wrap, hr, .md-toc, …')`), not by content sniffing, so it can't be fooled by a heading that merely mentions the word "table". A read-only (shared) note never gets `contenteditable` at all — `startEdit` checks `readOnly` before either edit path runs. Block-to-block movement (Enter splits/opens a new block, Backspace at the very start merges into the previous paragraph or steps into it, Arrow-Up/Down at the first/last line leaves the block) is reported back to `blogmode.js` (`onSplit`/`onMerge`/`onLeave`) because only it knows the block's line range in `#editor`'s source; `blogwyg.js` itself never touches `src` directly. `atStart`/`atEnd` compare the selection against the block's actual content element (`h*`/`p`/`ul`/`ol`/`blockquote`), not the `.blog-block` wrapper — `MD.render()`'s HTML ends in a literal `\n`, which lands as a trailing whitespace text node inside the wrapper, and comparing against the wrapper made every "caret at the last visible character" check silently read as "not yet at the end" (Arrow-Down never left the block; this was caught by the round-trip corpus test, not by eye). Pasting a file into a WYSIWYG block still becomes its own block exactly like the textarea path (`opts.onFiles` → `wygPasteFiles`, which finishes the current edit and inserts after it, then `insertAfterLine`, the same call the textarea/drop paths use) — a plain-text paste handler that ignored `clipboardData.files` would otherwise make image paste silently do nothing the moment the focused block is WYSIWYG, which is the common case. `docToken`, bumped every `BlogMode.show()`, guards that upload against landing in the wrong note if the user has navigated away by the time it resolves (belt-and-braces: `onBlogChange` in `app.js` already drops a write for a note that isn't `blogNoteId`, so this only improves the toast message, not data safety). Table cells inside a table block are **not** handled here — a `kind: 'table'` block is excluded from `WYSIWYG_KINDS` entirely and goes through `js/tablegrid.js`'s own click-a-cell editor instead (see the Obsidian-style table editing bullet below); the two coexist because a table is never itself `contenteditable`.
- **Markdown pipeline (`markdown.js`):** marked (`breaks: true` — HackMD semantics, a source newline is a `<br>`; do not "fix" this back to the CommonMark default, users write one sentence per line and expect the preview to match the editor) + DOMPurify + highlight.js with custom tokenizer extensions for GitHub `> [!NOTE]` callouts, HackMD `:::info` containers (aliased onto the same callout HTML), `RISK:` callouts, `[toc]`, and ` ```lang= ` line-number fences. A fence with **no language** is highlighted through the **bash** grammar (`autoShell`, `ignoreIllegals: true`) with no visible language label — not `highlightAuto`, which was removed because it confidently mislabels pentest content (measured: `whoami` output → SQL with 69 spans, an NTLM hash → Ruby, a Cobalt Strike log → SQL). bash is safe *because* it is conservative: pasted terminal output (nmap/whoami/mimikatz/ls dumps, hashes) comes back with 0–1 spans and stays visually plain, while actual commands get their `#` comments / `"strings"` / `$vars` tinted; the label is left blank so an untagged block never claims to be bash. A setext underline that is a lone `-` does not make a heading (the `lheading` tokenizer override): under a list item that line is someone starting an empty sub-bullet, and CommonMark would turn the parent item's text into an `<h2>`. One indent level in `editor.js` is 4 spaces, and on a list line Tab/Shift+Tab move the whole line a level wherever the caret is. Images are referenced as `![alt](img:<id>)` and embedded PDFs as `![name](pdf:<id>)`; rendering resolves them through `Store.getImageBlob`, a session-lifetime cache of raw image bytes keyed by id that both the preview (`MD.resolveImages`) and PDF export (`MD.inlineImagesAsDataURL`) share, so an image-heavy note is fetched once total instead of once per surface. The cache holds the in-flight *promise*, not just the settled blob: `resolveImages` walks every `<img data-img-id>` synchronously, so a report that reuses one small icon several times issues that many `getImageBlob` calls before the first can possibly have resolved — caching only the settled value (the bug this replaced) let every one of them race past the empty cache and fire its own redundant GET, each competing for the same handful of per-origin connections; over a flaky link that's what turns "open a note with a repeated icon" into everything sitting broken for tens of seconds before popping in together. A rejected fetch deletes itself from the cache (checking the cached entry is still *this* promise before deleting, so a slow failure can't clobber a newer request already in flight) so the next caller gets a fresh attempt instead of a permanently poisoned `null`. `Store.getImage` (blob + `/meta`, for shapes/`canAnnotate`) stays the annotation editor's own call, since it is the only caller that needs metadata; `MD.invalidateImage`/`Store.invalidateImage` drop an id from the cache after annotation rewrites it.
- **Editor/preview line sync (`linesync.js`):** click a line on either side and that line is underlined on *both* sides — the editor row and the matching preview text, image or code line. Deliberately a companion pass outside `markdown.js` — it never touches `MD.render()`, a renderer, or an extension, so it cannot affect PDF export, the published e-book, or search, none of which call it. It takes the note's top-level blocks from `marked.lexer()` — the same `marked` instance, so the callout/container/RISK/`[toc]` extensions are included and each token is exactly one rendered block — finds each token's `raw` in the source (after the same CRLF and leading-tab normalisation marked applies) for its line range, and pairs tokens with the already-rendered preview DOM by *position* per kind — the Nth heading token with the Nth outermost `<h1..h6>`, and so on — the same idea `app.js`'s own `editorBlocks()`/`previewBlocks()` use for the split-view scroll anchors. Do not go back to a hand-written block scanner: the first version had one, and every construct where it disagreed with marked (a `<br>` or other raw-HTML line, indented code, a setext heading, a lazy continuation line, text right after a table, a pipe-less table, a link definition) added a phantom paragraph, so every later paragraph underlined its neighbour — and a lone `| grep` line looped forever. Elements are matched *outermost*, not as direct children, because a raw-HTML wrapper (`<details>`, `<div align="center">`) can enclose markdown blocks; the blocks a raw `html` token produces itself are counted in a `<template>` and skipped. Paragraphs and list items get split further at each `<br>` (breaks:true's one-newline-one-`<br>` guarantee, plus one more per literal `<br>` typed on a line), and un-numbered code blocks at each newline inside their `<code>` (line-numbered code already has one `<li>` per line), into one `<span class="sync-ln" data-line0 data-line1">` per source line, reusing `markdown.js`'s `splitHighlightedLines` tag-stack trick (generalized from splitting on `\n` to splitting on `<br>`, and from `<span>`-only to any tag, with void elements like `<img>`/`<input>` excluded from the open-tag stack since they have no closing tag to balance). Blockquote/callout/RISK-finding/mindmap blocks — and a code block as a whole, for its fence lines — are tagged as ONE coarse range instead — not addressable line-by-line the way plain text is — and a list item's own text is refined the same way but a *nested* sub-list inside it is left completely untouched, falling back to the outer `<li>`'s own coarse range. Every tagged element carries `data-line0`/`data-line1` directly (coarse containers *and*, where refined, the inner spans within them), so a preview click is just `closest('[data-line0]')` — nearest ancestor naturally wins over the coarser one further out. The editor side has no per-line DOM of its own; it reuses `edithl.js`'s existing one-`.cm-row`-per-source-line overlay purely as a paint target (a `.sync-hit` class), without changing `edithl.js` — and because edithl replaces every row on each input and resize, a `MutationObserver` on `.cm-lines` puts the class back. Both sides go through one `showHit(start, end)`: the editor rows for that range plus every preview element tagged with exactly that range, minus any element containing another hit (a one-line `<p>` and its own span share a range, and only `.sync-ln` is styled). In the preview a text line gets an underline, an image or PDF embed a bar under it (`text-decoration` cannot paint under a replaced element), a coarse block a bottom rule. Rebuilt on every `renderPreviewNow()`; afterwards, while the editor has focus the underline is re-derived from the caret, otherwise it is dropped on both sides, since the same line numbers may no longer hold the same text. In `renderPreviewNow()` it must run *before* `MD.resolveImages()`: splitting a paragraph or list item rewrites its `innerHTML`, which replaces its `<img>` elements, and on a cache miss `resolveImages` sets `src` asynchronously — in the other order the `src` lands on the discarded element, so every image in a paragraph or list item is blank when a note is opened and only appears after the next keystroke re-renders from cache (images in tables and callouts are unaffected, which makes it look intermittent).
- **PDF export (`pdf.js`):** builds a standalone HTML document (cover, TOC with page numbers, themes, watermark) and paginates it with `vendor/paged.polyfill.js` inside a same-origin iframe written via `document.write`, then prints. The in-app preview and the printed output are the same document.
- **Image library (`js/imagelib.js`, `GET /api/images` → `api.js:listImages`):** the 圖片管理 row at the bottom of the sidebar opens a gallery of every upload the caller owns (images and PDFs; metadata only) with the notes each one appears in, filtered as 全部 / 使用中 / 未使用 / 僅在垃圾桶 and, through a note picker (or the funnel on each 使用於 row), by note. The picker's list is the union of `images[].notes`, so it only offers notes the caller can see, and the status counts and footer totals follow the chosen note. "Used" is decided exactly like image visibility — `img:<id>` or `pdf:<id>` anywhere in note content — but over *every* note regardless of owner (`q.notesEmbeddingMedia` is only an `INSTR` prefilter; the exact matching is the `MEDIA_REF` regex), because an upload pasted into someone else's note is still in use and must not be offered as unused. A note the caller cannot read only increments `hiddenNotes`: never named, and its alt text never becomes the image's `name`. The caller's own trashed notes are returned with `trashed: true`, which is what 僅在垃圾桶 means. Note *versions* are not scanned, so an image shown as unused may still be referenced by an old version. - **Uploads are any file, and serving decides what a file may do.** `POST /api/images` takes any `Content-Type` (sanitised by `uploadMime`) plus the original name percent-encoded in `X-File-Name` (`images.name`). `server.js:sendUpload` serves only inert types as themselves — raster images, `application/pdf` (the in-note viewer needs it inline), SVG under a `sandbox` CSP — and everything else as an `application/octet-stream` attachment with `Content-Disposition` and `sandbox`. Keep it that way for every route that returns stored bytes (`/original` too): served under its claimed type, an uploaded `.js` satisfies `script-src 'self'` and an uploaded page runs in the app's origin. In notes: `![alt](img:<id>)` embeds an image, `![名稱](pdf:<id>)` embeds a PDF viewer, `[名稱](pdf:<id>)` shows the same PDF as a file link, `[名稱](file:<id>)` is any other attachment (`fileChipHTML` in `markdown.js`, via marked's `link` renderer, which returns `false` for ordinary links). Visibility and the library's "used" check (`getImage`, `MEDIA_REF`, `notesEmbeddingMedia`) know all three schemes; a new scheme must be added to all of them or its files 404 for share recipients and show as unused. Every upload path — paste, drop, toolbar 檔案, `/file`, the same in Blog, and the library's own 上傳檔案 — goes through `uploadFiles` in `app.js`. The sidebar entry and dialog are 檔案管理 (`imagelib.js`, still `ImageLib`, still `/api/images`).

A drop remembers the target block's *text* and finds it again when the upload returns, since line numbers may have moved meanwhile.
- **Link preview cards (`{%preview https://… %}`, `server/linkpreview.js`):** a block extension (`linkCardExtension`) renders only a frame with the address; `MD.resolveLinkCards` (called from `resolveImages`, and awaited by `inlineImagesAsDataURL` for PDF/book, which also inlines the thumbnail) fills title/description/image from `GET /api/link-preview`, with `textContent` only. - **Embed switch (`js/embedswitch.js`):** hovering an embedded PDF, a PDF file link, a link card or a web link that is its paragraph's only content shows one floating 「檔案｜預覽」/「連結｜預覽卡片」 bar (a `position: fixed` body child). - **Sort order (`js/sorting.js`, `PUT /api/order`):** the sidebar tree and the dashboard share one mode (`localStorage` `sortMode`: manual / name / created / updated) and one comparator. Manual order is `notes.position` / `folders.position`; a never-dragged row is `NULL` and sorts ahead of positioned ones (notes by last update, folders by name), which is exactly the order both lists had before this existed, so nothing moves until something is dragged. Pinned notes are first in every mode. A drop always sends the *whole* level in its new order (`api.js:saveOrder`, which also moves listed rows into that level and refuses a folder into its own subtree), via `placeItems` in `app.js`; dropping between rows in a non-manual mode switches to manual starting from the order on screen, while a plain move into a folder appends to that folder's manual order. `placeItems` also updates `state.current` when it is a different object from the `state.notes` entry — autosave sends `folderId`, and a stale one moves the note straight back. - **Image annotation (`annotate.js`):** shapes are stored as vectors alongside the untouched `original` blob; the flattened `data` blob is what notes and PDFs display. Only the image owner may annotate.
- **Version history (`server/api.js` + `js/versions.js`):** every text save also writes a row into `note_versions`. - **Mind maps (`mindmap.js`):** a ` ```mindmap ` fence holding an indented outline. The outline is the source of truth — searchable, mergeable, and readable as plain text — and the SVG is derived on every render. Layout is deterministic and DOM-free (text width is estimated from character classes) so the same picture comes out on screen, in print and in a published file. The model and Markdown come straight from `TableTool._parse`/`_serialize` (`js/table.js`) — the same model the classic editor's floating table toolbar uses — so both surfaces round-trip a table identically. `blogmode.js` owns the write-back: every change re-serialises the whole table and `writeTable()` splices just that block's source lines back into `#editor`'s value, so autosave, merge, search, PDF, book and versions are untouched. Two write paths: `softWrite` (per keystroke inside a cell — updates the source but does *not* re-render, so the cell editor stays put) and `commit` (structural ops, cell navigation, or closing — re-renders and reopens the cell named by `gridFocus`, which is the table's order index among all `<table>`s plus `{r,c}`; that index survives add/remove-column/row because those never add or remove a table). It only attaches to a block whose `kind === 'table'` (a table inside a `:::` container stays whole-block-edited), coexists with the column-width grips (`.blog-col-grip`, a separate concern), and is off for read-only shared notes. `render()`/`detach()` call `TableGrid.closeAll()` so a stray cell editor or menu can't outlive a re-render. **A synthetic in-page test can't see whether a real drag starts (see the drag-and-drop note above), but the grid's cell edit / menu ops / drag reorder are all driveable with ordinary dispatched mouse+key events on the handles and `.tg-cell-edit`, since none of it uses the native HTML5 drag pipeline** — it is plain `mousedown`+`mousemove`+`mouseup`.
- **Table column widths are draggable in Blog and stored in `note.meta.tableWidths`.** Markdown has no column-width concept, so the widths (an array indexed by the table's document order; each entry an array of per-column percentages) live in meta, invisible in the source. They are applied to the *rendered DOM* by `MD.applyColWidths(container, widths)` / `MD.setTableCols(table, pct)` (`markdown.js`), which injects a `<colgroup>` and switches only that table to `display:table; table-layout:fixed; width:100%` (marking it `data-colw` so overlong cells wrap) — a table with no stored widths, or a stored entry whose length no longer matches the columns, is left in the default `display:block; width:fit-content` layout. Every render surface calls it on its own container: `renderPreviewNow`/`exportPDF` in `app.js`, `book.js` (both the reader and the standalone export), and `blogmode.js`'s `applyTableWidths` (per render). The *drag* is Blog-only: `attachTableResize` puts a `.blog-col-grip` on each internal column boundary; dragging (`startColDrag`) resizes the boundary's left column and its right neighbour absorbs the change (total stays 100%, each column ≥ 6%), live via `setTableCols`, and on mouseup persists through `opts.onTableWidths` → `setTableWidths` in `app.js`, which writes `state.current.meta.tableWidths` and `scheduleSave()`s (bookkeeping meta change, no rev bump). `.blog-col-grip` is excluded in `onClick` so grabbing it does not enter block edit. Index drift when tables are added/removed/reordered is the accepted cost of not polluting the markdown.
- `vendor/` holds pinned minified copies of marked, DOMPurify, highlight.js (+ powershell, dos grammars, github light/dark themes that `app.js` swaps on theme change), paged.js, and the webfonts (`vendor/fonts/`: Inter and Noto Sans TC subsets behind `fonts.css`). There is no CDN usage.
